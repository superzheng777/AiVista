# AiVista 发现能力模块

> 对应迭代：前端迭代 7——灵感、关注与关键词搜索
> 当前状态：设计中
> 维护规则：本文记录发现能力的页面范围、交互、接口消费与验收；代码、测试、接口契约或交互规则变化时必须同步修改。

## 1. 目标与范围

在现有公开灵感首页和公开作品详情基础上，讨论并确定三类灵感列表的前端体验；后续讨论与实现只围绕这三类进行：

- 灵感列表。
- 关注列表。
- 关键词查询结果。

公开作品详情继续使用 `/inspirations/[imageId]` 及既有覆盖层规则。热门排序、评论、广告位和未经后端契约确认的静态入口不在范围内。

## 2. 已确认约束

- 发现结果只展示当前公开作品，图片项继续消费统一 `GenerationAssetImageResponse` 映射的前端模型。
- 站内点击任一公开作品时，详情通过拦截路由覆盖当前来源页面；直接访问或刷新详情 URL 时，以灵感首页为背景。
- 灵感、关注和关键词查询的分页均只能使用服务端返回的不透明游标；不得在前端推算页码、游标或排序分数。
- 三类列表均采用瀑布流、无限滚动和图片按需加载；这些展示与加载策略不改变服务端游标分页，仍以每批最多 60 项继续读取。
- 灵感页与发现能力不订阅 SSE；刷新或重新进入页面时读取新的服务端快照。
- 灵感列表与关键词查询允许匿名访问；关注列表要求登录。无论访问者身份如何，均不得突破公开作品的可见性边界。
- 不在 URL、`localStorage`、埋点或错误监控中写入签名 URL、提示词或作品正文。

## 3. 关键决策记录

已确认灵感页只包含灵感列表、关注列表和关键词查询结果。关键词查询只匹配公开作品的标题和描述。以下事项待讨论确认后写入本表：入口信息架构、关键词查询触发方式与 URL 状态、灵感/关注列表切换模型、三类结果的排序语义、初始与继续加载规则、空态文案、移动端布局和可访问性细节。

| 决策事项 | 最终结论 | 原因与取舍 | 对实现的影响 |
| --- | --- | --- | --- |
| 灵感列表范围 | 灵感列表、关注列表、关键词查询结果 | 作为迭代 7 后续讨论的共同边界。 | 不呈现热门排序或其他未确认的发现入口。 |
| 访问条件 | 灵感列表与关键词查询允许匿名访问；关注列表要求登录。 | 三类结果都只包含当前公开作品，关注关系本身属于登录用户的私有数据。 | 关注列表接口须鉴权；其余两类接口按匿名或登录查看者返回对应互动状态。 |
| 搜索字段 | 仅匹配公开作品标题与描述。 | 不将提示词、作者昵称、评论或标签纳入首版检索范围。 | 后端查询、索引与前端搜索提示均仅围绕标题和描述。 |
| 搜索输入边界 | 前端只提交一个 `keyword` 字符串；后端负责校验、规范化、拆词、匹配和排序。 | 不在客户端实现分词、关键词权重或布尔语法，保证 Web 与未来 App 的结果一致。 | 前端不得传 tokens、权重或排序参数；输入限制、单字符搜索提示和错误文案待后端规则确定。 |
| 接口组织 | 采用三个语义独立的列表接口：灵感、关注与搜索。 | 三类查询的认证、输入、缓存和后续限流约束不同，不将其隐藏在一个 `mode` 参数分支中。 | 前端为三个列表分别建立查询函数与缓存键，但复用统一图片 DTO、分页响应和不透明游标消费逻辑。 |
| 关注列表排序 | 按作品发布时间倒序，发布时间相同再按作品 ID 倒序。 | 关注流首先满足“查看所关注作者最新公开作品”的直接预期，不引入额外推荐信号。 | 前端按服务端顺序渲染；游标由服务端绑定 `publicAt` 与 `imageId`。 |
| 分页批大小 | 三类列表每次最多加载 60 个作品；不向服务端传 `limit`。 | 瀑布流布局与图片懒加载不改变服务端分页单位，统一批量上限可控制首屏与继续加载的负载。 | 前端收到 `nextCursor` 后才请求下一批；每批渲染 60 个卡片，并对未进入视口的图片使用懒加载。 |
| 灵感排序信号 | 发布时间、单图点赞数、作者粉丝数、作者获赞总数；不加入随机排序。 | 同时兼顾新鲜度、单作品反馈和作者社区信号，并保证同一排序快照中顺序可复现；归一化、权重、衰减周期和候选内容范围待后端排序方案确定。 | 前端不自行计算或重排综合分数，只按服务端返回顺序展示。 |
| 灵感排序一致性 | 首次加载绑定全站共享的排序快照，继续加载始终使用该快照。 | 实时点赞和关注会改变质量信号；若每页实时重排，将产生重复或漏项。 | 前端只保存并回传不透明 `nextCursor`，不保存或推断 `snapshotId`、分数和名次；游标过期时清空列表后重新加载。 |
| 搜索排序与匹配 | 关键词相关性第一；同等相关性下使用灵感快照名次。后端按固定匹配等级和文本分数排序。 | 搜索首先满足明确查询意图，不能由点赞数或发布时间压过更匹配的作品；动态全文检索浮点分数不直接作为前端分页依据。 | 前端不自行高亮或排序来改变服务端结果；匹配等级、关键词输入规则和高亮需求待后端契约确定。 |
| 瀑布流布局技术 | 不以 CSS Grid Lanes（`display: grid-lanes`）作为生产实现基础；可持续关注其标准和浏览器支持。 | 该语法所在的 CSS Grid Level 3 仍是编辑草案，浏览器兼容数据将其标为实验性；当前 Chrome、Edge 和 Firefox 未实现，不能覆盖项目的主要访问环境。 | 采用兼容性方案实现真实瀑布流、无限滚动和图片懒加载；不得把 CSS Grid Lanes 当作唯一布局或仅以 `@supports` 降级为普通网格。 |
| 服务端顺序与瀑布流放置 | 服务端顺序定义作品进入瀑布流的先后；允许布局算法将下一张作品放入当前最短车道。 | 最短车道放置仅改变视觉位置，不修改列表数据、游标或服务端决定的进入顺序，是实现错落瀑布流的必要展示行为。 | 前端不得按点赞、发布时间、分数或关键词重新排序 `items`；可按到达顺序逐项分配至最短列。车道等宽，卡片不跨列。 |
| 签名图片 URL 与懒加载 | 卡片进入预加载视口前，如 URL 已失效或将在安全窗口内失效，则按图片 ID 刷新 URL；图片加载失败时只允许刷新并重试一次。 | 当前公开列表签发的是短期私有 OSS URL，离屏图片可能在用户滚动到它之前失效；不能把已过期的首批 URL 当成永久资源。 | 首版复用既有单张公开作品读取与 `needsImageUrlRefresh` 判断，只在内存更新该卡片的 URL 字段；不持久化签名 URL，也不对每一张首批图片预先刷新。 |

### 5.1 瀑布流渲染设计

灵感、关注和搜索共用同一个客户端瀑布流容器。列表数据的唯一输入是按服务端顺序拼接的 `items`；容器不读取排序分数、快照标识或搜索匹配信息。

```text
CursorPage.items（保持原数组顺序）
        ↓
MasonryFeed 逐项消费
        ↓
选择当前视觉高度最短的车道；同高时选择最左侧车道
        ↓
只将当前项目追加到该车道，不移动既有项目
```

- 初次加载后，按响应数组从左到右逐项分配至最短车道。
- 后续每批最多 60 项到达时，在现有车道高度的基础上继续逐项追加；不得重新分配此前已展示的项目。
- 使用单一、按 `items` 原顺序排列的 DOM 容器；卡片以布局层计算出的绝对坐标展示在对应车道。不得为每列创建独立的子数组/DOM 包装，否则键盘与读屏顺序会变成列优先而非服务端到达顺序。
- 仅当容器宽度跨越响应式断点、导致车道数量改变，或调用“刷新并从头读取”时，才允许清空布局状态并按当前完整数组顺序重新分配。
- 车道数量以容器宽度决定，首版采用 `1 / 2 / 3 / 4 / 5` 列；每条车道等宽。当前统一实现以 `220px` 为最小车道宽度、`16px` 为车道间距、最多五列，由容器实际可用宽度推导列数，不让页面各自维护媒体查询。
- `GenerationAsset.width`、`height` 用于图片区域的 `aspect-ratio` 占位和车道高度预估；卡片元信息区域使用固定高度或受限行数，避免图片加载、标题换行导致明显的后续布局跳动。
- 图片实际尺寸与预估存在偏差时，可通过单卡 `ResizeObserver` 校正该车道的后续估算高度，但不得为此移动已展示卡片。
- 卡片保留 DOM 的数据到达顺序；最短车道只改变视觉位置。键盘焦点与读屏顺序以 DOM 顺序为准，实施后须人工验证焦点移动是否可理解。

### 5.2 分页、加载与图片策略

- 数据层继续使用 React Query 的 `useInfiniteQuery`，查询函数只返回统一的 `{ items, nextCursor }`。
- 每个列表语义使用独立 `queryKey`：灵感、关注和规范化后的搜索关键词不得共享分页缓存。
- 底部哨兵放在所有车道容器之后；使用 `IntersectionObserver` 和预取边距触发加载。`hasNextPage`、`isFetchingNextPage` 或继续加载错误时不得发起重复请求。
- 首批加载显示瀑布流骨架；继续加载只在底部显示状态，不覆盖或重排已展示卡片；继续加载失败提供仅重试该批的操作。
- 图片使用已有签名 URL、`width`、`height`、`loading="lazy"` 和 `decoding="async"`；首屏少量图片可例外地优先加载。不得把签名 URL 写入持久化客户端存储。
- 长列表卡片可使用 `content-visibility: auto` 作为渲染优化；虚拟化不是首版前置条件，只有实测多个分页后的 DOM/滚动性能不足时再单独引入。

## 6. API、前端模型与状态管理

接口按查询语义拆分，不使用 `mode` 参数混合匿名、认证与搜索请求：

| 前端请求 | 后端路径 | 访问条件 | 已确认参数 |
| --- | --- | --- | --- |
| 灵感列表 | `GET /api/inspirations` | 匿名或登录 | `cursor` 可选；每批最多 60 项。 |
| 关注列表 | `GET /api/inspirations/following` | 必须登录 | `cursor` 可选；每批最多 60 项。 |
| 关键词搜索 | `GET /api/inspirations/search` | 匿名或登录 | `keyword` 必填，`cursor` 可选；每批最多 60 项；前端只传字符串，输入长度、空白、单字符和非法输入规则待确认。 |

三类请求均返回统一图片 DTO 的 `{ items, nextCursor }` 分页响应；游标仅可在创建它的列表语义、排序规则、快照和搜索词中继续使用，不得跨接口、跨快照或跨搜索词复用。前端分别建立查询函数和缓存键，复用 DTO 映射与通用游标分页逻辑。灵感与搜索的快照、排序、游标过期、刷新、重试和缓存细节以后端同名模块文档为准。
