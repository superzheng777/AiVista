# AiVista 发现能力模块

> 对应迭代：前端迭代 7——灵感、关注与关键词搜索
> 当前状态：设计中
> 维护规则：本文记录发现能力的页面范围、交互、接口消费与验收；代码、测试、接口契约或交互规则变化时必须同步修改。

## 1. 目标与范围

在现有公开灵感首页和公开作品详情基础上，提供三类语义清晰的发现体验：

- 灵感列表。
- 关注列表。
- 关键词查询结果。

公开作品详情继续使用 `/inspirations/[imageId]` 及既有覆盖层规则。灵感与关注列表均按最新公开时间展示；搜索作为独立 URL 状态按文本相关性展示。热门、随机、复杂个性化推荐、评论和广告位不在范围内。

## 2. 已确认约束

- 发现结果只展示当前公开作品，图片项继续消费统一 `GenerationAssetImageResponse` 映射的前端模型。
- 站内点击任一公开作品时，详情通过拦截路由覆盖当前来源页面；直接访问或刷新详情 URL 时，以灵感首页为背景。
- 灵感、关注和关键词查询的分页均只能使用服务端返回的不透明游标；不得在前端推算页码、游标或排序分数。
- 三类列表均采用瀑布流、无限滚动和图片按需加载；首次请求最多读取 20 项，后续每次携带游标最多读取 40 项。
- 灵感页与发现能力不订阅 SSE；刷新或重新进入页面时重新读取当前公开数据。
- 灵感列表与关键词查询允许匿名访问；关注列表要求登录。无论访问者身份如何，均不得突破公开作品的可见性边界。
- 搜索词作为页面导航状态写入 `/inspirations/search?q=...`，以支持刷新、前进后退和分享结果页；签名 URL、作品提示词和作品正文不得写入 URL、`localStorage`、埋点或错误监控，搜索词也不得进入埋点或错误监控上下文。

| 页面信息架构 | 发现首页顶部提供搜索框，主体使用“灵感 / 关注”切换；提交搜索进入 `/inspirations/search?q=...`。 | 浏览状态与明确查询意图分离；搜索 URL 可刷新、回退和分享，不把结果隐藏在仅存在于内存的临时状态中。 | 搜索结果页以规范化后的 `q` 建立独立查询键；清空搜索或返回时恢复来源列表及其滚动缓存。 |
| 关注列表排序 | 按作品发布时间倒序，发布时间相同再按作品 ID 倒序。 | 关注流首先满足“查看所关注作者最新公开作品”的直接预期，不引入额外推荐信号。 | 前端按服务端顺序渲染；游标由服务端绑定 `publicAt` 与 `imageId`。 |
| 分页批大小 | 三类列表首次最多加载 20 个作品，后续每次最多加载 40 个作品；不向服务端传 `limit`。 | 较小首批缩短首屏响应并减少初始签名 URL，较大后续批次降低持续滚动时的请求频率。 | 首次查询不带游标；收到 `nextCursor` 后才请求最多 40 项的下一批，并对未进入视口的图片使用懒加载。 |
| 灵感列表排序 | 按作品公开时间倒序，公开时间相同再按作品 ID 倒序。 | 首版明确表达“最新公开作品”，不把热门、推荐和作者历史影响力混为一个未知榜单。 | 前端只按服务端返回顺序展示，不读取或计算点赞权重、作者权重、综合分数或快照名次。 |
| 灵感列表刷新 | 无游标请求从当前最新作品开始；继续加载使用服务端返回的稳定游标。 | `publicAt` 与图片 ID 已能提供稳定 keyset 分页，无需维护全站排名快照。 | 手动刷新时清空该列表分页缓存并从头加载；新发布作品在刷新或重新进入后出现。 |
| 搜索排序与匹配 | 标题、公开正向提示词和描述的相关性优先；同等相关性下优先较新的作品。 | 搜索首先满足明确查询意图；点赞数、作者粉丝数和作者累计获赞不应压过更匹配的作品。 | 前端不自行高亮、计算或重排结果；只保存并回传搜索接口的不透明游标，搜索结果不依赖灵感列表缓存或排名。 |
| 瀑布流布局技术 | 不以 CSS Grid Lanes（`display: grid-lanes`）作为生产实现基础；可持续关注其标准和浏览器支持。 | 该语法所在的 CSS Grid Level 3 仍是编辑草案，浏览器兼容数据将其标为实验性；当前 Chrome、Edge 和 Firefox 未实现，不能覆盖项目的主要访问环境。 | 采用兼容性方案实现真实瀑布流、无限滚动和图片懒加载；不得把 CSS Grid Lanes 当作唯一布局或仅以 `@supports` 降级为普通网格。 |
| 服务端顺序与瀑布流放置 | 服务端顺序定义作品进入瀑布流的先后；允许布局算法将下一张作品放入当前最短车道。 | 最短车道放置仅改变视觉位置，不修改列表数据、游标或服务端决定的进入顺序，是实现错落瀑布流的必要展示行为。 | 前端不得按点赞、发布时间、分数或关键词重新排序 `items`；可按到达顺序逐项分配至最短列。车道等宽，卡片不跨列。 |
| 签名图片 URL 与懒加载 | 卡片进入预加载视口前，如 URL 已过期或无效，则按图片 ID 刷新 URL；图片加载失败时只允许刷新并重试一次。 | 当前公开列表签发的是短期私有 OSS URL，离屏图片可能在用户滚动到它之前失效；不能把已过期的首批 URL 当成永久资源。 | 首版复用既有单张公开作品读取与 `needsImageUrlRefresh` 判断，只在内存更新该卡片的 URL 字段；不持久化签名 URL，也不对每一张首批图片预先刷新。 |

## 5. 页面、路由与交互设计

- `/inspirations` 为发现首页，默认展示“灵感”；页面顶部提供搜索框，主体提供“灵感 / 关注”切换。
- “关注”状态使用 `/inspirations?view=following`，以支持刷新和前进后退；未知 `view` 回退为默认灵感列表。匿名用户进入关注状态时展示登录引导，不把未认证错误渲染成普通加载失败。
- 搜索框提交规范化后的非空文本时进入 `/inspirations/search?q=...`；搜索结果页从 `q` 恢复输入框和查询状态，修改并再次提交后从第一页读取新结果。
- 搜索结果不与灵感或关注混排，不提供首版“热门”“推荐”“最新”等搜索排序开关；后端返回顺序是唯一业务顺序。
- 从任一列表点击作品仍进入 `/inspirations/[imageId]` 详情；关闭详情或浏览器返回时恢复来源 URL、查询缓存和可恢复的滚动位置。直接访问或刷新详情 URL 时，以默认灵感首页作为背景。
- 三类列表分别提供首次加载、空结果、首次加载失败、继续加载失败和结束状态；继续加载失败只重试当前下一批，不清空已展示内容。
- 桌面与移动端复用相同信息架构；具体控件尺寸、窄屏布局、键盘焦点和文案在实现前完成验收定义。

### 5.1 瀑布流渲染设计

灵感、关注和搜索共用同一个客户端瀑布流容器。列表数据的唯一输入是按服务端顺序拼接的 `items`；容器不读取排序分数或搜索匹配信息。

```text
CursorPage.items（保持原数组顺序）
        ↓
MasonryFeed 逐项消费
        ↓
选择当前视觉高度最短的车道；同高时选择最左侧车道
        ↓
只将当前项目追加到该车道，不移动既有项目
```

- 初次加载后，按响应数组从左到右逐项分配至最短车道。
- 后续每批最多 40 项到达时，在现有车道高度的基础上继续逐项追加；不得重新分配此前已展示的项目。
- 使用单一、按 `items` 原顺序排列的 DOM 容器；卡片以布局层计算出的绝对坐标展示在对应车道。不得为每列创建独立的子数组/DOM 包装，否则键盘与读屏顺序会变成列优先而非服务端到达顺序。
- 仅当容器宽度跨越响应式断点、导致车道数量改变，或调用“刷新并从头读取”时，才允许清空布局状态并按当前完整数组顺序重新分配。
- 车道数量以容器宽度决定，首版采用 `1 / 2 / 3 / 4 / 5` 列；每条车道等宽。当前统一实现以 `220px` 为最小车道宽度、`16px` 为车道间距、最多五列，由容器实际可用宽度推导列数，不让页面各自维护媒体查询。
- `GenerationAsset.width`、`height` 用于图片区域的 `aspect-ratio` 占位和车道高度预估；卡片元信息区域使用固定高度或受限行数，避免图片加载、标题换行导致明显的后续布局跳动。
- 图片实际尺寸与预估存在偏差时，可通过单卡 `ResizeObserver` 校正该车道的后续估算高度，但不得为此移动已展示卡片。
- 卡片保留 DOM 的数据到达顺序；最短车道只改变视觉位置。键盘焦点与读屏顺序以 DOM 顺序为准，实施后须人工验证焦点移动是否可理解。

### 5.2 分页、加载与图片策略

- 数据层继续使用 React Query 的 `useInfiniteQuery`，查询函数只返回统一的 `{ items, nextCursor }`。
- 每个列表语义使用独立 `queryKey`：灵感、关注和规范化后的搜索关键词不得共享分页缓存。
- 底部哨兵放在所有车道容器之后；使用 `IntersectionObserver` 和预取边距触发加载。`hasNextPage`、`isFetchingNextPage` 或继续加载错误时不得发起重复请求。
- 首批加载显示瀑布流骨架；继续加载只在底部显示状态，不覆盖或重排已展示卡片；继续加载失败提供仅重试该批的操作。
- 图片使用已有签名 URL、`width`、`height`、`loading="lazy"` 和 `decoding="async"`；首屏少量图片可例外地优先加载。不得把签名 URL 写入持久化客户端存储。
- 长列表卡片可使用 `content-visibility: auto` 作为渲染优化；虚拟化不是首版前置条件，只有实测多个分页后的 DOM/滚动性能不足时再单独引入。

## 6. API、前端模型与状态管理

接口按查询语义拆分，不使用 `mode` 参数混合匿名、认证与搜索请求：

| 前端请求 | 后端路径 | 访问条件 | 已确认参数 |
| --- | --- | --- | --- |
| 灵感列表 | `GET /api/inspirations` | 匿名或登录 | `cursor` 可选；无游标最多 20 项，携带游标最多 40 项；按公开时间与图片 ID 倒序。 |
| 关注列表 | `GET /api/inspirations/following` | 必须登录 | `cursor` 可选；无游标最多 20 项，携带游标最多 40 项；按公开时间与图片 ID 倒序。 |
| 关键词搜索 | `GET /api/inspirations/search` | 匿名或登录 | `keyword` 必填，`cursor` 可选；无游标最多 20 项，携带游标最多 40 项；搜索标题、公开正向提示词和描述。前端只传字符串，输入长度、空白、单字符和非法输入规则待确认。 |

三类请求均返回统一图片 DTO 的 `{ items, nextCursor }` 分页响应；游标仅可在创建它的列表语义、排序规则和搜索词中继续使用，不得跨接口或跨搜索词复用。前端分别建立查询函数和缓存键，复用 DTO 映射与通用游标分页逻辑。灵感和关注查询键不含客户端排序参数；搜索查询键包含规范化后的 `q`。排序、游标、刷新、重试和缓存细节以后端同名模块文档为准。
