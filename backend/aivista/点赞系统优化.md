# AiVista 点赞系统优化方案

> 文档状态：讨论草案，尚未实施
>
> 建立日期：2026-08-17
>
> 维护规则：本文独立记录点赞系统优化讨论，不代表当前生产契约。方案完成实现并通过验收后，再把最终结论合并到《社区身份与互动模块》《关键词搜索模块》及前端对应文档，并删除或归档本文。

## 1. 优化目标与边界

本次优化拟把高频点赞状态与图片点赞计数从 MySQL 同步事务迁移到单节点 Redis，由异步消息最终持久化到 MySQL，以降低热门图片和热门作者记录的行锁竞争，并保持前端点赞反馈及时。

本次讨论只涉及点赞、取消点赞、点赞计数、点赞列表、作者获赞数、互动通知和搜索索引所依赖的点赞变更。关注、收藏、发布审核、评论和推荐排序公式不在本方案内；但撤销发布与重新发布会改变点赞公开周期，必须纳入一致性设计。

本文必须区分三类内容：

- **当前事实**：现有代码已经实现并运行的行为。
- **已确认方向**：讨论中已经达成一致、后续设计不得无理由偏离的内容。
- **待确认事项**：仍有多个可行方案，实施前必须明确取舍。

## 2. 当前实现事实

当前点赞系统以 MySQL 为事实源，尚未接入 Redis：

1. `PUT /api/inspirations/{imageId}/like?publicationVersion={version}` 确保点赞，`DELETE` 确保取消点赞，成功返回 `204 No Content`。
2. `generation_image_likes(user_id, image_id, publication_version, liked_at)` 只保存当前有效点赞关系；主键为 `(user_id, image_id, publication_version)`，取消点赞时直接删除关系。
3. `generation_images.like_count` 保存图片点赞数，`users.received_like_count` 保存作者获赞总数。
4. 一次实际状态变化会在同一 MySQL 事务中锁定图片，新增或删除关系，更新图片计数和作者获赞数，并写入搜索同步 Outbox；首次点赞他人作品时还会创建互动通知及其 Outbox。
5. 撤销发布时同步删除当前公开周期的全部点赞关系，将图片点赞数归零并扣减作者获赞总数。
6. `publicationVersion` 隔离同一图片的不同公开周期，旧详情不能修改重新发布后的点赞状态。
7. 当前点赞限流是单实例 JVM 内存令牌桶，不是 Redis 限流。
8. 当前 RabbitMQ 已配置 correlated publisher confirm；点赞写链路尚未向 RabbitMQ 发布持久化消息。

现有实现优点是关系、图片计数和作者计数强一致，接口幂等且公开周期边界明确。主要扩展风险是热门图片行、热门作者行的同步竞争，以及撤销热门作品时批量删除点赞关系造成的长事务。

## 3. 已确认的产品与架构方向

### 3.1 前端交互

- 点赞和取消点赞继续表达“最终目标状态”，不是无语义的状态翻转：`PUT` 表示确保点赞，`DELETE` 表示确保未点赞。
- 前端先乐观更新，再在短防抖窗口内合并同一图片的连续操作，只向后端发送窗口结束时的最终目标状态。
- 明确的业务失败应回滚乐观状态；网络超时、连接中断等结果未知错误不能直接认定 Redis 未执行，应使用相同目标状态幂等重试或重新读取服务端状态后校正。
- 前端防抖、合并和按钮禁用只减少请求并改善体验，不承担多标签页、多设备、请求重试、消息重复和乱序的一致性保证。

### 3.2 Redis 角色

- 当前部署前提是单节点 Redis，因此一次 Lua 脚本可以原子操作不同点赞键；未来迁移 Redis Cluster 时需重新处理跨 slot 原子性。
- Redis 拟成为点赞交互的实时状态源，而不只是可随时丢弃的普通缓存。Redis 必须配置持久化且点赞键不得使用会自动淘汰业务状态的缓存策略。
- Redis 优先维护“用户点赞了哪些图片”，不维护“每张图片的全部点赞用户集合”。该方向更符合批量判断当前用户点赞状态和按时间读取用户点赞列表的查询需求，也避免在 Redis 中按图片复制全部用户关系。
- 图片点赞计数使用独立 Redis 计数键；用户点赞列表使用按点赞时间排序的 ZSET。

建议键模型：

```text
likes:user:{userId}
  ZSET(score = 服务端 likedAt，member = imageId:publicationVersion)

like:count:{imageId}:{publicationVersion}
  STRING(当前实时点赞数)
```

列表返回一批图片时，可用 `ZMSCORE` 批量判断当前用户点赞了哪些图片，用 `MGET` 批量读取图片点赞数，禁止逐图发起 Redis 或数据库请求。

### 3.3 点赞列表

- 当前用户自己的点赞状态必须以 Redis 实时状态为准。
- 他人的公开点赞列表属于低频页面，可以继续从 MySQL 查询并接受数秒级最终一致。
- 他人点赞列表仍需按用户隐私设置以及图片当前公开状态、`publicationVersion` 进行 MySQL 校验；已撤销或版本失效的作品不得返回。
- 自己的点赞列表究竟直接读取 Redis ZSET，还是也读取最终一致的 MySQL，尚未最终确定。若要求刚操作后立即出现在本人主页，应读取 Redis 候选并由 MySQL 批量组装有效图片。

### 3.4 异步持久化

- Redis 成功后，点赞状态最终异步持久化到 MySQL。
- RabbitMQ 使用 durable queue、persistent message 和 Publisher Confirm；消费者必须幂等，不能对重复消息无条件执行计数 `+1/-1`。
- MySQL、搜索索引、作者获赞数和他人点赞列表允许在短时间内落后于 Redis 实时状态。
- Redis 到 RabbitMQ 之间无法通过普通代码形成跨系统原子事务。“MQ 通常稳定”和“Redis 开启持久化”可以降低故障概率，但不能从逻辑上消除 Redis 已成功而消息未留下的窗口。

## 4. 暂定请求链路

在当前单节点 Redis 前提下，一次目标状态变更拟通过 Lua 完成：

```text
客户端 PUT / DELETE
        ↓
认证、公开状态与 publicationVersion 校验
        ↓
Redis Lua
├─ 判断当前 ZSET 成员状态
├─ 状态实际变化时 ZADD 或 ZREM
├─ 状态实际变化时 INCR 或 DECR 图片计数
├─ 生成服务端时间与操作顺序标识
└─ 返回 Redis 最终状态和计数
        ↓
发布 RabbitMQ 持久化消息
        ↓
消费者幂等更新 MySQL
        ↓
异步更新作者获赞数、互动通知与搜索投影
```

重复 `PUT` 或重复 `DELETE` 不产生新的关系变化，不修改计数，也不应重复创建互动通知。时间必须由后端或 Redis 生成，不能使用客户端时间作为一致性依据。

现有接口成功返回 `204`。优化后是否改为返回 Redis 最终的 `liked` 与 `likeCount` 尚待确认；返回最终状态有利于前端校正乐观计数，但属于 API 契约变更。

## 5. MySQL 持久化模型草案

异步消息可能重复或乱序，取消点赞时若仍直接删除关系行，数据库将失去“更新的取消操作已经发生”的证据。暂定把有效关系表改为状态表或新增状态投影：

```text
user_image_like_states
- user_id
- image_id
- publication_version
- liked
- liked_at
- updated_at
- operation_sequence
PRIMARY KEY (user_id, image_id, publication_version)
```

字段语义：

- `liked`：MySQL 当前已持久化的最终状态。
- `liked_at`：最近一次从未点赞变为点赞的服务端时间，只为点赞列表排序和展示服务。
- `updated_at`：最近一次点赞或取消点赞的服务端时间。
- `operation_sequence`：只用于拒绝重复或较旧的异步消息，不用于用户展示。

消费者只允许较新的操作覆盖当前状态：

```text
incoming.operationSequence > stored.operationSequence  → 接受
incoming.operationSequence <= stored.operationSequence → 重复或旧消息，忽略
```

因此 `operation_sequence` 解决的是这类问题：用户先点赞、后取消，但取消消息先落库、旧点赞消息因重试后到达；没有顺序字段时，旧消息会错误恢复点赞。单消费者和 RabbitMQ FIFO 可以降低乱序概率，但并发消费、重试队列、重新投递和未来扩容都可能破坏严格顺序，因此暂定保留顺序字段。

操作顺序标识可以由 Redis Lua 中的全局 `INCR` 生成；如果最终采用 Redis Stream，也可以直接使用 Stream ID。两种方式尚未确定。

图片计数拟拆到独立持久化表：

```text
generation_image_like_stats
- image_id
- publication_version
- like_count
- updated_at
PRIMARY KEY (image_id, publication_version)
```

拆表能够隔离图片本体的高频更新，但不能单独消除热门图片计数行竞争。由于 MySQL 计数是异步投影，可以按消息批量聚合，或周期性用 Redis 当前计数覆盖校正，避免每条消息都对同一行执行一次更新。

取消点赞的 `liked=false` 状态属于防乱序墓碑，不能立即删除。墓碑清理周期、消息最长重试周期和安全水位尚待设计。

## 6. Redis 到 RabbitMQ 的可靠性选择

目前有两个可实施级别，尚未最终选定。

### 6.1 简化方案：接受极小丢失窗口

```text
Redis Lua 成功
→ 后端发布 RabbitMQ
→ 等待 Publisher Confirm
→ 失败时有限重试
```

优点：链路较短，复用现有 RabbitMQ。缺点：后端可能在 Redis 成功、消息可靠发布前退出，导致该操作只存在于 Redis。Redis 持久化不能自动补发这条消息。

采用本方案必须明确接受极低概率的点赞持久化遗漏，并增加 Redis/MySQL 对账修复。失败重试必须由有边界的后台机制执行，不能无限占用 HTTP 请求线程。

### 6.2 严格方案：Redis Stream 作为 Redis Outbox

```text
Redis Lua
├─ 修改实时状态
└─ XADD like:events
        ↓
后台 Consumer Group 持久化 MySQL
```

`like:events` 确实是在同一个 Redis 中增加一条持久化事件流，可理解为 Redis 侧队列或追加日志，不是新增 Redis 实例。它使实时状态变化与待持久化事件能够在一次 Redis 原子操作中完成。

如果 Stream 消费者直接写 MySQL，点赞持久化不必再经过 RabbitMQ；如果继续中继 RabbitMQ，则形成 `Redis Stream → Relay → RabbitMQ → MySQL` 两级消息链路，只有在需要复用 RabbitMQ 路由或多个下游消费者时才值得承担这项复杂度。

## 7. 尚未解决的问题

### 7.1 Redis 持久化与单点风险

- 采用 RDB、AOF `everysec` 还是 AOF `always` 尚未确定；不同策略对应不同写延迟与故障恢复点。
- 单节点 Redis 没有副本故障切换，机器或磁盘故障会直接影响点赞可用性和未落库状态。
- Redis 冷启动时，是先从 MySQL 恢复全部状态，还是按用户懒加载，尚未设计。
- 点赞键不得被普通 LRU/LFU 策略淘汰；内存容量、ZSET 增长和清理策略需要估算。

### 7.2 请求结果未知

Redis 已执行但 HTTP 响应丢失时，前端看到的是网络失败。接口必须保持目标状态幂等，并定义网络错误后的重试或状态查询；不能对所有异常一律回滚。

### 7.3 Redis 与公开生命周期竞态

点赞与撤销发布并发时，必须保证失效公开周期不能继续接受点赞。需要决定：

- 每次点赞是否仍同步查询 MySQL 当前公开状态；
- 是否把图片当前公开版本缓存到 Redis，并在 Lua 中校验；
- 撤销发布如何使 Redis 版本立即失效；
- 已成功写入 Redis、但持久化时发现版本失效的事件如何回滚或清理。

`publicationVersion` 必须继续进入 Redis member、计数 key、消息和 MySQL 主键，不能因为引入 Redis 而取消。

### 7.4 作者获赞总数

`users.received_like_count` 是当前最明显的作者热点行。优化后不应在每次点赞主链路中同步更新。需要确定由消息增量聚合，还是按图片统计周期性重算；无论哪种方案，都需要可重复执行的对账机制。

### 7.5 互动通知

当前规则是同一点赞者对同一图片公开周期最多通知一次，取消后再点赞不重复通知，自赞不通知。异步化后需要继续保证这个唯一语义，不能因为消息重复创建多条通知。通知创建失败不得回滚 Redis 点赞状态。

### 7.6 搜索索引

Meilisearch 的 `likeCount` 只允许最终一致。应以 MySQL 已持久化计数还是 Redis 实时计数作为索引同步来源尚待确定；为保持可重建性，默认应继续以 MySQL 为搜索投影事实来源。

### 7.7 计数校正

消息重复、遗漏、Redis 恢复和人工数据修复都可能造成计数偏差。必须设计：

- 用户状态与 MySQL 状态的增量或全量对账；
- Redis 图片计数与有效用户点赞状态的校验；
- MySQL 图片计数和作者获赞数的重算命令；
- 对账频率、批次大小、失败重试和告警阈值。

## 8. 当前方案合理性判断

| 事项 | 当前判断 | 说明 |
| --- | --- | --- |
| 前端乐观更新、防抖和最终状态合并 | 合理，已确认 | 减少无意义写入，但不能代替服务端幂等和顺序控制。 |
| Redis 使用用户到图片的 ZSET | 合理，已确认方向 | 同时支持批量点赞状态判断和按时间读取本人点赞列表。 |
| Redis 单独保存图片计数 | 合理，已确认方向 | 适合公开列表批量读取；必须只在关系实际变化时增减。 |
| Redis 保存图片到全部用户的 SET | 当前不采用 | 不能直接支持用户点赞列表，并完整复制全站关系，内存成本较高。 |
| 他人点赞列表读取 MySQL | 合理，已确认 | 页面低频，可接受数秒最终一致，但必须复核隐私和公开状态。 |
| Redis 后异步落 MySQL | 有条件合理 | Redis 已成为实时事实源，必须明确持久化、故障恢复、消息遗漏和对账策略。 |
| MQ 一般稳定，因此无需可靠事件记录 | 事实不足 | 稳定只能降低概率，不能消除 Redis 与 MQ 双写窗口；是否接受该窗口仍待产品取舍。 |
| 用时间戳解决消息顺序 | 不充分 | 时间可用于展示和列表排序；消息新旧应使用单调顺序标识。 |
| MySQL 取消点赞直接删除关系 | 不适合乱序异步消费 | 删除会丢失较新的取消版本，需要墓碑状态或同等的幂等顺序记录。 |
| 拆出图片计数表 | 合理但作用有限 | 能隔离高频写，不能单独消除同一热门图片计数行竞争。 |
| Redis Stream | 技术上合理，待决定 | 能消除 Redis 状态与待持久化事件之间的窗口，但会增加一条消息日志。 |

## 9. 参考方案评审：掘金《从零设计一个高并发点赞系统》

参考文章：[从零设计一个高并发点赞系统：缓存+MQ异步持久化实战](https://juejin.cn/post/7662951063265263643)。本节只提炼和评审文章方案，不把文章示例直接视为本项目的最终设计。

### 9.1 文章方案摘要

文章采用“Redis 实时读写、Kafka 异步削峰、MySQL 最终持久化、定时校对”的总体结构：

```text
客户端防抖与乐观更新
        ↓
网关鉴权、滑动窗口限流
        ↓
Redis Lua 原子修改点赞关系与计数
        ↓
Kafka 按 targetId 分区
        ↓
消费者批量 Upsert MySQL
        ↓
凌晨从 MySQL 聚合计数并覆盖 Redis
```

文章提出三份 Redis 数据：

```text
like:{type}:{targetId}
  HASH(field = userId, value = likedAt)

like_count:{type}:{targetId}
  STRING(count)

user_like:{userId}
  ZSET(score = likedAt, member = targetId)
```

MySQL 使用点赞状态表和计数快照表。点赞状态表以 `(user_id, target_id, target_type)` 唯一，保留 `status=1/0`，消费者批量执行 `INSERT ... ON DUPLICATE KEY UPDATE`。文章以 `targetId` 作为 Kafka 分区键，希望同一内容的消息保持顺序；生产端建议 `acks=all`、回调重试和幂等生产者，消费端建议业务完成后手动提交 offset。

### 9.2 值得采用的部分

| 文章设计 | 本项目结论 |
| --- | --- |
| 前端防抖、合并与乐观更新 | 采用，但仍由服务端保证幂等和结果未知恢复。 |
| Redis Lua 同时判断关系并修改计数 | 采用；只有关系实际变化时才修改计数。 |
| MySQL 使用唯一键和状态 Upsert | 采用其思路，并增加 `publicationVersion` 与消息顺序字段。 |
| MQ 批量消费、批量落库 | 采用；需要先在批次内按关系键压缩到最新状态。 |
| 同一业务键路由到同一消息分区 | 采用其原则；RabbitMQ 需要等价的稳定路由或消费者侧顺序保护。 |
| 用户维度 ZSET 支持按点赞时间读取 | 采用；它也是本项目批量判断当前用户点赞状态的主要 Redis 结构。 |
| 滑动窗口限流 | 可采用 Redis 化，但保留本项目已有的“用户全站 + 用户/图片”两级限制，不能只按用户限制。 |
| MySQL 保留取消状态 | 适合异步乱序场景；不能再沿用当前取消即删除且不留版本的模型。 |

### 9.3 文章示例不能直接照搬的问题

#### 9.3.1 三份 Redis 状态没有在同一脚本维护

文章声明同时维护图片关系 Hash、图片计数 String 和用户点赞 ZSET，但展示的 Lua 只修改前两项，没有 `ZADD/ZREM user_like:{userId}`。按示例实现后，“我赞过的”列表会与实时点赞状态不一致。

本项目当前不需要展示“某张图片被哪些用户点赞”，因此不保留图片到用户的完整 Hash。优先只维护：

```text
用户 → 图片 ZSET
图片 → 点赞计数 STRING
```

这能覆盖现有查询，同时避免在 Redis 中保存两份完整关系索引。若未来产品确实需要公开点赞者列表，再单独评估反向索引及其一致性成本。

#### 9.3.2 文章声称使用 Redis Cluster，但 key 设计不支持跨 key Lua

文章 Lua 同时操作：

```text
like:post:123
like_count:post:123
```

在 Redis Cluster 中，这两个 key 默认可能位于不同 hash slot，Lua 会产生 `CROSSSLOT`，除非使用相同 hash tag，例如：

```text
like:{post:123}
like_count:{post:123}
```

文章还需要同时修改 `user_like:{userId}`，它天然按用户分片，通常无法与图片计数 key 放入同一 slot。因此文章的三 key 全原子方案不能直接扩展到 Cluster。

本项目当前是单节点 Redis，第一版可以用 Lua 原子修改用户 ZSET、图片计数和可选事件流；但必须在文档中明确这是单节点假设。未来改 Cluster 时，应把原子核心缩小为用户关系状态和可靠事件，图片计数改为异步投影，或重新设计分区。

#### 9.3.3 MQ 发送代码没有保证“发送成功后再返回”

文章示例调用异步 `send()` 后立即返回，只在回调中记录失败。即使配置 `acks=all`，也仍存在 Redis 已成功、进程在消息可靠确认前退出的窗口。日志回调不是补偿机制，`@Transactional` 也不管理 Redis 和 Kafka 的跨系统事务。

本项目必须在两种方案中明确选择：接受该极小窗口并对账，或把待持久化事件与 Redis 状态原子写入 Redis Stream。不能用“MQ 一般不会坏”替代一致性边界说明。

#### 9.3.4 “幂等操作仍发消息”需要顺序保护

文章在 Redis 返回“状态未变化”时仍发送目标状态消息，希望修复数据库。这一思路有价值，但消息中的时间戳没有参与 MySQL 条件更新。旧的重复点赞消息如果晚于新的取消消息落库，可能把 MySQL 状态恢复为点赞。

本项目若对无变化请求也发送修复事件，消费者必须只接受更新的 `operationSequence`；不能只执行无条件 `status = VALUES(status)`。前端时间和应用服务器墙钟都不能单独承担顺序判定。

#### 9.3.5 批量 Upsert 前缺少同关系压缩

同一批次可能包含同一用户、同一图片、同一公开周期的多次操作。直接把所有事件组成批量 Upsert，不仅产生多余数据库写，也使最终状态依赖批次内部顺序和数据库具体执行行为。

消费者应先按 `(userId, imageId, publicationVersion)` 分组，只保留 `operationSequence` 最大的最终状态，再批量条件 Upsert。

#### 9.3.6 定时校对方向存在事实源冲突

文章主链路把 Redis 作为实时正确状态，MySQL 由 MQ 最终同步；但凌晨任务又按 MySQL 统计并覆盖 Redis。如果恰好有 Redis 成功而 MQ 消息丢失，MySQL 是落后的，定时任务会把 Redis 中正确计数覆盖成错误计数。

而且文章校对只覆盖图片计数，没有修复图片关系 Hash、用户 ZSET和 MySQL 状态关系。因此它不是完整对账。

本项目必须先明确每类数据的事实源：

- 在异步写后方案中，Redis 是近期实时关系和计数事实；MySQL 是最终持久化副本，但可能暂时落后。
- 正常对账不能无条件以 MySQL 覆盖 Redis。需要比较操作水位，或从带顺序的关系事件/状态重建两边。
- Redis 灾难恢复时可以用 MySQL 恢复到最后持久化水位，但这表示接受水位之后尚未落库数据的恢复点损失。

#### 9.3.7 数据库计数表在文章流程中没有闭环

文章设计了 `like_count` MySQL 表，但展示的 Kafka 消费者只 Upsert `like_record`，凌晨任务再从关系表聚合并写回 Redis，没有说明何时维护 MySQL `like_count`。该表在示例中实际没有完整写入链路。

本项目需要二选一：

- MySQL 计数表作为异步投影，由消费批次按最终关系变化聚合更新并定期重算；或
- 不存独立 MySQL 计数快照，查询/重建时从有效关系聚合，但需要接受聚合成本。

不能同时建表又不定义维护者。

#### 9.3.8 文章没有覆盖本项目的领域边界

文章是通用帖子/评论示例，缺少本项目必须处理的：

- `publicationVersion` 公开周期隔离；
- 点赞与撤销发布并发；
- 撤销发布后的 Redis 状态和历史关系清理；
- 作者 `receivedLikeCount`；
- 首次点赞互动通知且取消后再点赞不重复通知；
- Meilisearch 点赞数投影；
- 他人点赞列表隐私；
- 从认证身份获取 `userId`，禁止相信请求体中的用户 ID。

这些不是次要扩展，而是 AiVista 点赞正确性的组成部分。

#### 9.3.9 热点内容仍然是单 key 热点

Redis Cluster 可以分散不同内容的流量，但单个明星内容的关系 Hash和计数 key仍只落在一个分片，无法依靠 Cluster 自动拆开单热点。文章提出的本地 Caffeine只能用于允许短暂陈旧的展示计数，不能缓存并直接裁决“当前用户是否点赞”或执行写操作。

第一版可以依赖限流和单 Redis 承载；只有压测或生产指标证明单图片计数 key成为瓶颈后，才考虑分片计数、排队合并或热点降级。

### 9.4 参考文章对本项目方案的影响

阅读文章后，本项目主方向不需要反转，但需要收紧为：

```text
前端目标状态合并
        ↓
后端认证、限流、公开周期校验
        ↓
单节点 Redis Lua 原子修改用户 ZSET 与图片计数
        ↓
可靠性方案二选一：
  A. RabbitMQ Publisher Confirm + 接受极小窗口 + 完整对账
  B. 同一 Lua 写 Redis Stream，再异步持久化
        ↓
消费者按关系键和 operationSequence 压缩
        ↓
条件 Upsert MySQL 状态表
        ↓
异步投影作者计数、通知和搜索索引
```

文章能够证明这种架构是常见可行方向，但文章末尾“支撑千万级日活”的陈述没有给出压测环境、QPS、延迟、硬件、故障演练和数据规模，不能作为本项目容量结论。是否需要该复杂度仍应由 AiVista 的预期流量和压测数据决定。

## 10. 下一步决策顺序

实施前建议依次确认：

1. 是否明确接受“Redis 已成功但 RabbitMQ 未留下消息”的极低概率持久化遗漏。
2. 选择直接 RabbitMQ 简化方案，还是 Redis Stream 可靠事件方案；不重复叠加两级消息，除非确认存在多个下游路由需求。
3. 明确 Redis 是实时事实源时的对账方向，禁止无水位地用可能落后的 MySQL 覆盖 Redis。
4. 确定 Redis 持久化、禁止淘汰、容量与冷启动恢复策略。
5. 确定 `operation_sequence` 的生成方式、批次内最终状态压缩和 MySQL 墓碑保留策略。
6. 确定 MySQL 图片计数表是否保留，以及唯一负责维护它的投影链路。
7. 确定点赞成功响应继续使用 `204`，还是返回 Redis 最终状态与计数。
8. 设计撤销发布与 Redis 当前公开版本之间的原子边界。
9. 确定作者获赞数、搜索索引、互动通知和计数对账的异步投影方式。
10. 最后再拆分数据库表、Redis Lua、消息消费者和前端交互的具体实施步骤。

在以上关键选择确定前，本文只用于方案讨论，不应据此直接改造当前点赞写链路。
