# AiVista 收藏与发布模块

> 对应迭代：后端迭代 4——收藏、异步发布与官方消息
> 当前状态：设计中
> 维护规则：本文记录迭代 4 的范围、约束、设计结论和实施进度；代码、测试、接口或数据结构变化时必须同步修改。

## 1. 目标与范围

本迭代基于个人生成资产实现：收藏与收藏筛选、异步发布私有图片、我的发布列表、已发布作品删除，以及发布失败的官方消息通知。

发布成功后，私有原图被复制为独立公开 OSS 副本，系统返回直接指向该副本的稳定公开 URL。本迭代不提供公开社区列表、公开详情、他人主页、点赞、关注、推荐或互动消息。

## 2. 已确认规则

| 主题 | 规则 |
| --- | --- |
| 权限 | 仅图片所有者可收藏、取消收藏、发布或删除自己的未删除私有资产；仅发布记录所有者可删除自己的处理中或已发布作品。 |
| 收藏 | 收藏为 `generation_images` 上的所有者标记；支持单张和条件式批量变更：全部已收藏选择时统一取消收藏，含任一未收藏项时仅将未收藏项设为收藏。未来收藏他人公开作品时另建关系表，不复用本字段。 |
| 发布输入 | 客户端仅提交图片 ID、标题和可选描述。标题必填、1–100 个字符；描述最多 500 个字符。 |
| 生成配置读取 | 发布记录保存 `source_task_id`，提示词、模型、提示词优化、`n`、比例与尺寸均从不可变且不删除的 `generation_tasks` 单次关联读取。不得接受客户端提交或改写提示词。 |
| 公开副本 | 复制私有快照至独立公开作品 OSS bucket 的不可猜测对象路径；私有 bucket 与 `object_key` 不变。数据库只保存公开对象键，公开 URL 由部署配置 `AIVISTA_PUBLIC_MEDIA_BASE_URL` 与对象键动态拼出。当前不接 CDN。 |
| 公开链接失效 | 删除成功后，数据库记录立即不再参与公开查询，公开详情立即 `404`；随后异步删除公开 bucket 对象、失败持续重试。已下载或已被浏览器缓存的文件无法收回。未来接入 CDN 时另增加缓存刷新。 |
| 当前有效发布 | 每张图片存在 `QUEUED`、`PROCESSING` 或 `PUBLISHED` 记录时不得再次提交。用户删除已发布作品后，若私有资产仍存在，可再次发起一条全新的发布；新记录不得复用旧公开副本或旧链接。 |
| 私有资产与发布 | 发布请求被受理后，发布记录拥有独立的不可变图片快照。删除私有资产不会取消处理、删除发布记录或清理公开副本；处理中或已发布作品均可独立继续其生命周期。 |
| 发布作品删除 | 处理中或已发布作品均可从我的发布列表删除；删除发布记录及发布专属快照，已发布时另删除公开副本，不删除私有资产。删除后私有资产的内部发布状态回退为 `NONE`。 |
| 失败通知 | 发布失败不出现在发布记录列表中，改为创建持久化官方消息，含后端映射的用户可理解原因；不得暴露 OSS 路径、异常堆栈或第三方原始错误。 |
| 创建型命令幂等 | 创建生成任务、发布、未来支付、额度购买和导出均使用项目级防重表；收藏、删除、消息读写等状态型操作不使用该表。 |

## 3. 发布状态机与异步执行

发布请求返回 `202 Accepted`，只表示请求已被接收。发布记录是异步工作的权威状态，不复用图像生成任务状态。

```text
QUEUED -> PROCESSING -> PUBLISHED
  ^          |
  |          +-> FAILED
  +----------+ 可恢复失败重新排队；总执行次数最多 3 次
```

- 本迭代没有人工或自动内容审核；后台工作器只负责将发布专属快照复制为公开副本。前端将 `QUEUED`、`PROCESSING` 均展示为“发布处理中”。
- 只有 `PUBLISHED` 才返回公开 URL 并计入有效发布。
- `FAILED` 为终态，且绝不可被客户端展示为发布成功。
- 发布创建时将私有资产的内部 `publication_state` 设为 `QUEUED` 并关联本次发布 ID；工作器领取后设为 `PROCESSING`，发布成功时设为 `PUBLISHED`，发布失败时仅在 `current_publication_id + publication_version` 匹配时回退为 `NONE`。删除处理中或已发布作品时沿用同一条件回退规则，避免旧异步工作影响后续新发布。
- 异步执行采用可靠事件/Outbox 投递；失败记录须带稳定、可安全展示的原因，并触发官方消息。对外原因必须由后端映射，禁止透传 OSS 路径、异常堆栈或第三方原始错误。
- 每条发布记录总共最多执行 3 次（首次执行计入）；公开副本复制的明确失败、执行超时及工作器崩溃恢复共用 `publish_attempt_count`。耗尽次数后转为 `FAILED` 并创建官方消息。
- 用户刷新时通过 REST 快照读取状态；本迭代不为发布状态发送 SSE。发布失败落库后，经 Outbox 向该用户的既有 SSE 推送轻量通知事件和未读数量；消息详情仍由 REST 查询。

## 4. 数据模型

### 4.1 资产收藏

在 `generation_images` 增加仅所有者可见的 `favorited BOOLEAN NOT NULL DEFAULT FALSE` 和索引 `(user_id, favorited, deleted_at, created_at DESC, id DESC)`；资产列表以 `all/favorited` 筛选并保持现有不透明游标排序。收藏仅是资产所有者的布尔标记，不建立独立收藏表，不记录收藏时间或备注，也不支持跨用户收藏。软删除图片不出现在任何收藏筛选结果中。

同时增加仅供发布命令控制的 `publication_state`（`NONE`、`QUEUED`、`PROCESSING`、`PUBLISHED`）、`current_publication_id` 与 `publication_version`。这些字段不进入私有资产 DTO 或资产页展示，仅用于阻止重复发布、保证终态回退与隔离迟到工作消息。

`publication_version` 初始为 `0`，每次将资产关联到新发布、撤销当前发布或回退当前发布状态时递增。所有异步工作器回写资产内部发布状态均必须同时匹配 `current_publication_id` 和 `publication_version`；条件不匹配时更新 `0` 行并直接结束，不得覆盖较新的撤销或重新发布状态。例如，发布 A 受理后版本为 `1`，用户撤销 A 后版本递增为 `2`，任何仍携带版本 `1` 的迟到工作消息均无法再将该资产标记为 `PUBLISHED`。该版本字段为服务端并发保护，不进入 API DTO。

### 4.2 发布记录

新增 `image_publications`（名称在迁移评审时最终确定），至少包含：

- `BIGINT` 发布 ID、来源图片 ID、来源任务 ID、所有者 ID；对外 ID 一律序列化为字符串；
- 标题 `VARCHAR(100)`、可空描述 `VARCHAR(500)`；仅保存用户发布时填写的内容；
- `QUEUED`、`PROCESSING`、`PUBLISHED`、`FAILED` 状态，以及发布记录软删除时间；
- 发布专属的私有图片快照对象键和不可变公开对象键。服务端在复制快照前生成一次内部 UUID `publicationToken`，并以 `publications/{taskId}/{imageId}/{publicationToken}/snapshot.png` 与 `publications/{taskId}/{imageId}/{publicationToken}/image.png` 分别作为私有和公开对象键；该 token 不对外暴露、不是数据库主键或客户端幂等键。公开对象键可在处理中存在但仅 `PUBLISHED` 时返回公开 URL。不保存任何私有签名 URL 或完整公开 URL。`snapshot_object_key` 全局唯一并建立唯一索引，供发布记录约束和孤儿快照精确比对；
- `publish_attempt_count TINYINT UNSIGNED NOT NULL DEFAULT 0`、内部稳定 `failure_code VARCHAR(64) NULL`、创建/完成时间及发布记录自身的 `version BIGINT NOT NULL DEFAULT 0`；用户可见失败文案只写入官方消息。领取 `QUEUED` 任务进入 `PROCESSING` 时原子递增执行次数，最多 3 次；每次发布状态变更均条件匹配该发布记录的版本并递增。`PROCESSING` 连续 3 分钟未更新时按 `updated_at` 恢复重试，不增加 `processing_heartbeat_at`；
- 私有快照与公开副本各自独立的清理字段：`snapshot_cleanup_status` / `public_cleanup_status`（`NONE`、`PENDING`、`PROCESSING`、`DONE`）、尝试次数、下次重试时间、领取时间与安全错误摘要。清理器以领取时间防止重复执行，超时后恢复；删除 OSS 对象本身幂等，对象不存在也记为 `DONE`。快照在成功、失败或撤销时按需清理，公开副本仅在发布失败或撤销已发布作品时清理。清理失败回到 `PENDING` 并退避重试，不设次数上限；清理失败不改变已撤销发布的可见性或发布状态。

`generation_images` 只承载私有资产列表与详情，不返回发布状态或公开作品信息。我的发布列表及未来灵感列表均以 `image_publications` 为权威数据源。我的发布列表使用 `GET /api/my-publications?cursor=<opaque>&limit=30`，默认 `30`、最大 `60`，按发布记录创建时间倒序并使用不透明游标，展示当前用户的 `QUEUED`、`PROCESSING` 与已发布作品；前端将前两者统一显示为“发布处理中”。响应顶层一次性返回当前作者的 `userId`、昵称与头像，列表项不重复作者摘要；作者资料每次查询时从 `users` 实时读取。每个列表项均为完整作品详情快照：`publicationId`、`imageId`、状态、标题、可空描述、图片 URL 与过期时间、创建/完成时间，以及通过 `source_task_id` 查询的最终正向/负向提示词、模型、提示词优化开关、生成数量、画幅和最终尺寸；前端打开详情时不再发起单作品详情请求。处理中项的 `imageUrl` 为发布记录专属私有图片快照的短期签名 URL，附带过期时间，并复用资产页现有 10 分钟签名、到期前 30 秒刷新和图片加载失败刷新机制；已发布项的 `imageUrl` 由公开 bucket 基础域名与对象键动态拼出，过期时间为空。最终提示词和配置不冗余写入发布记录，仅在当前用户的我的发布列表中返回；公开社区另行设计其可见范围。灵感列表仅展示他人的 `PUBLISHED` 作品，并在未来按作者 ID添加关注能力，因此在该未来多作者列表中逐项携带作者摘要。删除私有资产不影响处理中或已发布记录，也不改变私有资产行上的内部 `publication_state`；已软删除发布记录和失败记录不向用户展示。每次发布提交保有独立发布 ID；已发布作品删除后，若私有资产仍存在，可创建新的发布 ID。发布记录的 `version` 仅作用于该条记录，第二次发布创建新的记录并从 `0` 开始；资产上的 `publication_version` 才跨多次发布递增，用于保护“当前发布关联”。

为保证同一图片最多一条有效发布，`image_publications` 增加由数据库自动计算的生成列 `active_image_id`：当记录未软删除且状态为 `QUEUED`、`PROCESSING` 或 `PUBLISHED` 时取 `image_id`，其他情况为 `NULL`。对该列建立唯一索引 `uq_publications_active_image`。因此失败或已撤销记录不阻止重新发布，两个并发请求却无法同时创建同图有效发布。该索引是数据库的最终并发兜底；资产上的当前发布指针和版本号仍负责隔离迟到状态更新。

当前仅建立以下查询索引：`idx_publications_owner_list (owner_id, deleted_at, created_at DESC, id DESC)` 支撑我的发布游标分页；`idx_publications_processing_recovery (status, updated_at)` 查询超时的 `PROCESSING` 记录；`idx_publications_snapshot_cleanup (snapshot_cleanup_status, snapshot_cleanup_next_attempt_at, snapshot_cleanup_locked_at)` 与 `idx_publications_public_cleanup (public_cleanup_status, public_cleanup_next_attempt_at, public_cleanup_locked_at)` 分别供两类对象清理器领取到期任务。暂不为 `source_task_id`、标题、描述或未来社区查询预建索引。

`image_publications.image_id`、`source_task_id`、`owner_id` 分别以 `RESTRICT` 外键关联图片、任务与用户；`user_notifications.recipient_user_id` 以 `RESTRICT` 外键关联用户，可空 `image_id` 与 `publication_id` 同样以 `RESTRICT` 外键关联对应记录。所有业务删除均为软删除，不使用数据库级级联删除。当前仅实现 OSS 对象的异步清理，不新增通用数据库物理清理任务；未来须按防重记录、消息、图片和发布记录分别设计保留期、归档与按依赖顺序的物理清理策略。

发布作品可供迭代 4 的“做同款”使用：前端通过 `source_task_id` 读取最终提示词和用户可见生成配置后预填，用户确认后按既有创建任务链路生成新的 UUID 幂等键并提交。图生图所需的“用作参考图”不在本迭代实现。

### 4.3 官方消息

新增可扩展的 `user_notifications`，本迭代只写入和读取 `category = OFFICIAL` 的记录，至少包含：

- `BIGINT` 消息 ID 与接收用户 ID；
- `category VARCHAR(32)`，当前固定为 `OFFICIAL`；`event_type VARCHAR(64)`，当前仅 `PUBLICATION_FAILED`；
- 可空的关联图片 ID 与发布记录 ID；图片软删除后消息仍保留；
- `title VARCHAR(200)` 与 `content VARCHAR(500)`，均为后端映射的安全展示文案；
- `read_at`、创建时间与软删除时间。

不保存资产快照、签名 URL 或未读布尔值：官方消息列表仅返回关联 `imageId`，用户点击“查看作品”后才查询资产详情；未读由 `read_at IS NULL` 判断。

通知表仅建立 `idx_notifications_recipient_list (recipient_user_id, category, deleted_at, created_at DESC, id DESC)`，供当前用户读取全部未删除官方消息并按创建时间倒序返回；以及 `idx_notifications_recipient_unread (recipient_user_id, category, deleted_at, read_at)`，供按 `read_at IS NULL` 统计未读数。当前不按图片、发布记录或正文反查、筛选或搜索消息，因此不为这些字段额外建索引。

本迭代仅写入和查询官方消息；互动消息由点赞迭代扩展。未读状态独立于发布记录，打开消息抽屉不改变它。官方消息按创建时间倒序全量返回当前用户未软删除记录，不设自动清理期限；软删除消息不参与后续列表和未读统计。用户删除已发布作品不创建官方消息；本迭代仅对发布失败写入官方消息。

### 4.4 创建型命令防重

新增项目级 `idempotency_records`，以自增 `BIGINT` 为主键，至少包含 `owner_id`、`scope`、UUID v4 `idempotency_key`、规范化请求的 SHA-256 `request_fingerprint`、`resource_type`、`resource_id`、首次安全响应的 HTTP 状态和 JSON、创建时间及过期时间。设置 `UNIQUE(owner_id, scope, idempotency_key)` 与 `expires_at` 索引。响应中不得存储签名 URL、Token、内部错误或其他敏感字段。

同一创建操作使用相同 key 和相同指纹时，重放首次保存的响应；相同 key 与不同指纹返回 `409 IDEMPOTENCY_KEY_CONFLICT`；不同 key 则继续进行业务状态校验。防重记录、发布记录与 Outbox 必须在同一事务中写入。生成任务创建与发布的防重记录固定保留 30 分钟；每 10 分钟按 `expires_at` 索引分批删除最多 1,000 条过期记录。未来财务类命令不采用该短期策略，需单独设计长期订单与支付防重。

通用防重表实施时，直接替换当前 `generation_tasks` 的专用 `idempotency_key`、`request_fingerprint` 字段及 `(user_id, idempotency_key)` 唯一索引：生成任务创建改用 `scope = GENERATION_TASK_CREATE`，发布创建使用 `scope = PUBLICATION_CREATE`。当前开发阶段不保留旧字段、双写或数据兼容层；迁移同步调整生成任务实体、Mapper 和创建服务。

## 5. API、鉴权与读取边界

- 所有资产和消息接口均要求登录，并按当前用户过滤；图片、发布和消息 ID 对外以字符串返回。
- 既有 `GET /api/generation-images` 增加可选 `filter=all|favorited` 查询参数，缺省为 `all`。服务端先按当前用户、`deleted_at IS NULL` 与筛选条件过滤，再沿用 `created_at DESC, id DESC` 的不透明游标分页；不同筛选条件的游标不得混用。
- 收藏与取消收藏分别使用 `POST /api/generation-images/favorite` 与 `POST /api/generation-images/unfavorite`，请求体均为 `{"imageIds":["101","102"]}`。`imageIds` 非空且不得重复；单图传一个 ID。两接口均为幂等空成功响应：仅改变当前用户自己的未删除图片；他人、不存在或已删除图片不产生影响且按成功处理，避免泄露资源存在性或归属。
- 发布使用 `POST /api/generation-images/{imageId}/publications`，请求体为 `{"title":"...","description":"..."}` 并必带 UUID v4 `Idempotency-Key`。标题去除首尾空白后必填、1–100 个字符；描述可选、最多 500 个字符。服务端生成内部 `publicationToken` 与两条对象键，调用 OSS 将原私有资产复制为发布专属私有快照；快照成功后才开启短事务，写入 `QUEUED` 记录、资产发布状态、防重记录和 Outbox，最后返回 `202` 的安全受理快照 `{"publicationId":"...","status":"QUEUED","createdAt":"..."}`；不支持批量发布。为保持发布状态机简洁，不新增“准备中”状态：并发请求可在事务前短暂重复复制快照，随后由同图有效发布的唯一索引裁决。落库失败的请求立即补偿删除本次未引用快照；同键请求重新读取防重记录并重放首次 `202`，不同键按当前有效发布返回 `409`。快照创建失败时直接失败、不创建发布记录或官方消息；服务崩溃等无法补偿时，由低频任务扫描发布快照前缀下的对象：仅当当前时间达到对象创建时间加宽限期（默认 1 小时），且完整对象键未被任何 `image_publications.snapshot_object_key` 引用时，才删除该私有孤儿对象。相同 key 与不同指纹返回 `409 IDEMPOTENCY_KEY_CONFLICT`；不同 key 遇排队/处理中返回 `409 PUBLICATION_IN_PROGRESS`，遇已发布返回 `409 IMAGE_ALREADY_PUBLISHED`；参数或 UUID 不合法返回 `422`。响应不包含对象键、签名 URL、失败原因或内部状态。
- 排队、处理中或已发布作品均使用 `DELETE /api/publications/{publicationId}` 删除，无请求体或 `Idempotency-Key`。首次删除与同一所有者的重复删除均返回 `204`；不存在、非本人或无权访问返回 `404`。首次删除软删除发布记录，并在该记录的两组清理字段上安排私有快照清理；已发布时另安排公开副本清理，不删除私有资产。删除操作以 `current_publication_id + publication_version` 条件更新将私有资产内部发布状态回退为 `NONE`，迟到工作消息不得继续发布。
- 发布、收藏、条件式批量收藏、私有资产删除和已发布作品删除均必须在服务端再次校验归属和当前状态；当前不提供批量发布。删除发布作品是唯一的撤销发布流程；删除完成后，私有资产仍存在时允许以新的发布记录重新发布。
- 发布接口返回接收后的发布 ID 与 `QUEUED` 状态；私有资产查询仅返回资产和收藏状态，不返回发布摘要。我的发布列表从 `image_publications` 查询当前用户的排队、处理中与已发布作品，并将前两者映射为“发布处理中”；失败原因仅从官方消息读取。
- 官方消息列表只返回关联图片的可空 `imageId`，不拼接资产 DTO 或生成私有签名 URL。用户点击“查看作品”后调用 `GET /api/generation-images/{imageId}`；资产仍存在且对当前用户可见时，该接口返回与资产列表单项相同的 DTO，资产已删除、不存在或不再可见时返回 `404`，前端显示“该图片已删除”。
- 官方消息列表使用无查询参数的 `GET /api/official-messages`，按创建时间倒序返回当前用户全部未软删除消息 `items` 和当前用户全部未读官方消息的 `unreadCount`；每项包含消息 ID、事件类型、标题、安全内容、可空 `imageId`、创建时间与可空 `readAt`。本迭代不使用游标、`limit`、`nextCursor`、单条详情或搜索接口。
- 全部已读和全部清除分别使用 `POST /api/official-messages/read-all` 与 `POST /api/official-messages/clear-all`。前者更新当前用户全部未软删除且未读消息的 `read_at`，后者更新当前用户全部未软删除消息的 `deleted_at`；两者成功后以 `200` 返回操作完成后的实际全量 `{"unreadCount": n}`，不返回删除条数。操作完成后新到达消息不受影响。
- 单条读写使用 `PATCH /api/official-messages/{messageId}` 与 `{"read":true|false}`，设置目标状态而非切换状态；单条清除使用 `DELETE /api/official-messages/{messageId}` 并写入软删除时间。三者均以 `200` 返回操作完成后的实际全量 `{"unreadCount": n}`；他人、不存在或已清除消息不产生影响且按成功处理，避免泄露资源信息。每次成功读写或清除均写入同用户未读数变化 SSE Outbox。
- 公开 OSS 直链只提供图片二进制内容；本迭代不提供公开标题、描述或提示词详情 API，未来公开详情通过 `source_task_id` 读取相应内容。
- 发布要求客户端传递 UUID `Idempotency-Key`；同一次用户操作及网络重试复用该键，服务端通过项目级防重表重放首次 `202` 响应，不得创建重复发布任务或公开副本。服务端以图片为粒度串行化竞争请求：存在未软删除的排队、处理中或已发布记录时，携带不同幂等键的新请求被拒绝。已发布作品删除后，若私有资产仍存在，才允许以新 key 创建新发布。复制类可恢复失败与工作器异常恢复共享总共 3 次执行上限，不得以客户端状态替代服务端唯一性约束。
- 发布请求参数或 UUID 不合法返回 `422`；相同幂等键与不同请求返回 `409 IDEMPOTENCY_KEY_CONFLICT`；同图排队或处理中返回 `409 PUBLICATION_IN_PROGRESS`，同图已发布返回 `409 IMAGE_ALREADY_PUBLISHED`。受理前快照复制暂时不可用返回 `503 PUBLICATION_SNAPSHOT_UNAVAILABLE`，不创建发布记录或官方消息。删除发布或按需读取资产时，无资源、非所有者或已删除统一返回 `404`。认证继续沿用项目约定：HTTP `401` 响应体业务码 `40100` 由前端刷新 Access Token 后重放原请求，`40102` 表示刷新令牌或会话失效并清理会话；网络与 `5xx` 故障不等同用户登出。所有其他内部异常均使用统一系统错误，不暴露 OSS、RabbitMQ 或内部异常细节。

## 6. 可靠性与一致性

- 创建公开副本失败时不得将新记录标为 `PUBLISHED`。发布记录受理前必须先拥有独立的私有图片快照；之后公开副本复制只使用该快照，私有资产删除不影响异步发布和公开副本复制。
- 发布工作器只可用 `UPDATE ... WHERE status = 'QUEUED' AND version = ?` 将记录领取为 `PROCESSING`，并递增共享的 `publish_attempt_count`；重复/过期消息更新 0 行后直接确认、不计入次数。复制明确失败时，未耗尽 3 次则以版本条件更新回 `QUEUED` 并写入下一次执行事件；`PROCESSING` 连续 3 分钟未更新时，由定时恢复任务按相同次数上限条件恢复为 `QUEUED` 并写入新的 `PUBLICATION_EXECUTE` 事件。第三次仍未成功则转为 `FAILED`；迟到工作器的终态更新必须带版本条件。
- 当前发布链路不设 `processing_heartbeat_at`。公开副本复制为单一步骤，3 分钟无更新恢复已留有余量。当前 `app.generation.oss.read-timeout=30s` 是共享配置：影响后端下载生成结果、上传/删除私有 OSS 对象，以及未来若复用该客户端的发布复制；不影响签名 URL 的本地生成或浏览器加载签名图片。未来增加大文件复制、转码或其他长步骤时，再拆分发布专用客户端/超时，并由工作器定期更新心跳。
- 发布每次进入 `QUEUED` 后，若连续 3 分钟未被工作器条件领取为 `PROCESSING`，则以 `PUBLICATION_QUEUE_TIMEOUT` 收敛为 `FAILED`：仅在状态和版本仍一致时回退资产内部发布状态、安排快照与预分配公开对象清理，并创建一条官方失败消息。RabbitMQ 已确认接收但没有消费者属于该超时范围，不由 Outbox 投递失败计数处理。
- 公开副本复制收到明确失败响应后，第二次执行延迟 4 秒，第三次执行延迟 8 秒；该等待时间写入对应通用 Outbox 事件的 `available_at`。这里的 30 秒仅指单次 OSS 读取请求的客户端超时，区别于 4/8 秒的重试间隔和 3 分钟的处理卡死恢复阈值。
- 同一发布的每次复制均使用同一份不可变私有快照和预分配的固定公开对象键，不在执行前增加 `headObject` 预检。若复制已成功但工作器在写入 `PUBLISHED` 前崩溃，恢复执行再次覆盖同一对象即可；固定键、发布版本条件和 3 次执行上限共同保证不产生第二条发布记录或第二个公开对象。
- 公开副本复制成功并提交 `PUBLISHED` 后，立即将该发布的私有快照安排为异步清理；正常已发布作品只长期保留公开副本。进入 `FAILED` 时，私有快照和预分配的公开对象键均安排清理，即使公开对象不存在也按删除成功处理。发布删除时仅安排尚未成功清理的对应对象，所有对象清理失败均持续重试。
- `outbox_events` 直接重构为项目级通用可靠事件表，不再保留 `task_id`、`task_version`、`task_status` 等任务专用列。统一字段为 `id`、`event_type VARCHAR(64)`、`aggregate_type VARCHAR(64)`、`aggregate_id BIGINT`、`aggregate_version BIGINT`、`payload_json JSON`、`status`（`PENDING`、`PROCESSING`、`PUBLISHED`、`FAILED`）、`retry_count`、`available_at`、`locked_at`、`published_at`、`last_error VARCHAR(500)`、`created_at` 与 `updated_at`。`event_type` 表示消费者要执行的动作，`aggregate_type + aggregate_id + aggregate_version` 定位并校验对应业务记录，因而同一发布记录可分别产生执行、快照清理和公开副本清理等不同事件。`payload_json` 仅保存投递所需的安全、不可变附加参数，消费者仍须按聚合 ID 回读权威业务记录；不得保存 Token、签名 URL、OSS 对象键或原始异常。
- 生成任务执行使用 `GENERATION_TASK_EXECUTE`，发布执行使用 `PUBLICATION_EXECUTE`；生成状态变化、发布失败后的官方消息和 SSE 未读数变化使用各自的通知事件类型。所有业务状态变更、对应 Outbox 事件和必要的防重记录必须在同一数据库事务提交；每类事件由相应投递器领取和处理，不能把所有事件投递到同一个 RabbitMQ 队列。
- 路由固定为：`GENERATION_TASK_EXECUTE` 投递 RabbitMQ `generation.task.execute`；`PUBLICATION_EXECUTE` 投递 `publication.execute`；`PUBLICATION_SNAPSHOT_CLEANUP` 与 `PUBLICATION_PUBLIC_CLEANUP` 投递 `publication.cleanup`。生成状态、官方消息和未读数变化等用户级 SSE 通知由 Outbox 扫描后经应用内 SSE 分发器直接投递，不经 RabbitMQ；用户没有 SSE 连接时通知事件可直接完成，写入失败则按有限次数重试，客户端最终以 REST 快照对账。执行与清理任务隔离，避免慢清理占用发布消费者。
- 除对象清理外，异步投递和执行均最多尝试 3 次（首次计入）；三次仍失败时对应 Outbox 进入 `FAILED` 并保存安全错误摘要。发布执行事件失败时，若发布仍为 `QUEUED` 且版本一致，则收敛为发布 `FAILED`、条件回退资产内部发布状态、安排对象清理并创建一条官方消息。生成任务执行事件沿用同样的三次上限，在任务仍为 `QUEUED` 且版本一致时收敛为失败并返还额度。SSE 通知事件失败只记录 `FAILED` 与告警，不改变已持久化的业务状态。对象清理不设次数上限，持续退避重试至 `DONE`；达到告警阈值时记录运维告警但不停止清理。RabbitMQ 已确认接收、但暂无消费者属于队列积压，Outbox 仍为 `PUBLISHED`，不计为投递失败。
- 排队、处理中或已发布作品删除前必须取得明确确认；删除排队/处理中记录时停止后续发布并清理发布快照，删除已发布记录时另清理公开副本。清理失败须持续重试至成功，私有资产不参与该清理。
- 私有资产删除沿用 `POST /api/generation-images/delete`：仅标记当前用户私有资产删除并清理其私有原图，不读取、不改变发布记录或公开副本。资产已删除时，关联处理中或已发布作品仍可继续存在和访问。
- 发布失败的终态转换、官方消息创建和消息 SSE Outbox 必须在同一事务中完成，因此同一发布记录不会产生重复官方消息。
- 当前公开 bucket 不接 CDN；删除对象完成后旧公开 URL 即由 OSS 拒绝。未来接入 CDN 时，在清理成功后增加对应缓存刷新。
- 公开作品流与详情排期迭代 5：灵感列表只返回卡片摘要；`GET /api/publications/{publicationId}` 只查询未软删除的 `PUBLISHED` 发布记录，否则返回 `404`。该接口可被作者本人读取并复用同一公开结构；是否展示关注按钮由前端按 `author.userId !== currentUserId` 决定。我的发布不提供 `GET /api/my-publications/{publicationId}`。
- 未读官方消息持续计入用户的未读数量；点击单条消息标记已读，支持全部已读、单条改未读、单条清除和全部清除。全部已读作用于当前用户所有未读官方消息。清除操作写入软删除时间；全部清除由客户端二次确认后调用，清除消息不影响对应发布或资产状态。
- 全部已读和全部清除影响当前用户全部消息，客户端成功后不得只修改局部缓存，必须重新获取完整消息列表。
- 新官方消息 SSE 事件可携带完整的安全通知字段、可空 `imageId` 和未读数量，但不得携带资产快照、私有签名 URL、OSS 对象键、内部异常或第三方原始错误。
- 已读、改未读、单条清除和全部清除后，经同一用户级 SSE 向其他标签页推送未读数量变化；客户端的“重新连接”每次开启新一轮最多 3 次连接尝试。

## 7. 测试与验收要点

- 非所有者、已删除图片和不合法状态均不能改变收藏或发布。
- 发布后刷新仍能读取处理中；成功后仅返回新公开链接；失败创建官方消息且不出现在发布列表。

- 已发布作品删除的确认、私有快照和公开副本清理按既定顺序可靠执行。
- 通知的单条已读、全部已读、改未读、红点与清除行为互相独立且可持久化。
- 自动化与联调最低覆盖：同键重试仅创建一条发布、同键不同请求冲突、同图并发只有一条受理成功、撤销发布后的迟到工作消息不覆盖资产状态且可重新发布、发布失败按 4 秒/8 秒重试并只创建一条官方消息、两类对象清理失败持续重试且对象不存在按成功、消息全量读取及跨标签未读数同步、消息按需读取资产详情的成功与 `404` 删除提示，以及 `40100` 刷新重放、`40102` 清理会话和网络/`5xx` 不误登出。

### 8.1 迁移策略

当前开发数据库将在实施前删除并由 Flyway 从 V1 重新执行，因此本迭代采用单个 `V7` 结构切换迁移，不拆分兼容阶段，也不修改既有 V1–V6 历史迁移。V7 依次扩展 `generation_images`，新建 `image_publications`、`user_notifications`、`idempotency_records`，删除 `generation_tasks` 的旧幂等字段与唯一索引，并删除后按通用结构重建 `outbox_events` 及其全部索引。应用仅在所有迁移完成后启动，不保留双写、回填或过渡字段。该迁移只适用于清空后的开发数据库；未来存在真实业务数据时，必须另行设计非破坏性迁移。

### 8.2 已确认设计决策（2026-08-07）

- 删除发布作品等同撤销该发布：删除 `QUEUED` 或 `PROCESSING` 记录时停止后续发布并清理发布专属快照；删除 `PUBLISHED` 记录时撤销公开副本。两者均不删除私有资产；私有资产仍存在时允许创建新的发布记录重新发布。
- 收藏、取消收藏和私有资产批量删除只作用于当前用户自己的未删除图片；他人、不存在或已删除图片均按幂等成功处理，以免暴露资源是否存在或归属。发布作品删除仅作者可操作；不存在、非作者或已删除发布统一返回 `404`。
- 发布创建必须携带 UUID v4 `Idempotency-Key`。同一用户、同一范围内，相同键和相同请求重放首次 `202` 响应；相同键和不同请求返回 `409 IDEMPOTENCY_KEY_CONFLICT`；不同键遇同图有效发布记录时，按状态返回 `409 PUBLICATION_IN_PROGRESS` 或 `409 IMAGE_ALREADY_PUBLISHED`。服务端是唯一并发裁决方。
- 发布状态固定为 `QUEUED -> PROCESSING -> PUBLISHED`，失败进入终态 `FAILED`；前端将前两个状态统一展示为“发布处理中”。每条发布最多执行 3 次，明确失败依次延迟 4 秒、8 秒重试；`PROCESSING` 连续 3 分钟未更新时，按相同次数上限恢复重试。耗尽次数后创建一条不含内部敏感信息的官方消息。发布状态以 REST 快照为权威，SSE 仅推送失败消息和未读数变化。
- 发布受理前必须先创建发布专属私有快照；快照成功后才在同一事务内写入发布记录、Outbox 与防重记录并返回 `202`。后续发布只读取该快照，私有资产删除不影响已受理发布。成功后清理私有快照；失败或撤销时清理快照，已公开时另清理公开副本；清理失败持续重试。公开 URL 只在 `PUBLISHED` 返回，私有签名 URL 仅短暂存在于前端内存。快照已生成但数据库事务失败时立即补偿删除，无引用孤儿快照由低频任务回收。
- 官方消息使用全量读取：`GET /api/official-messages` 返回当前用户全部未软删除消息和全量未读数，不使用游标分页。每条消息仅携带可空 `imageId`，不携带资产快照或签名 URL；用户点击“查看作品”后才读取当前资产详情，若接口返回 `404` 则展示“该图片已删除”。前端以虚拟列表处理渲染，抽屉打开、收到新消息且抽屉已打开、读写或清除成功后重新获取完整列表，不做轮询或隐式截断。
- 打开消息抽屉不改变未读状态；点击消息正文或“查看作品”才将该消息设为已读。单条读写使用显式 `PATCH {"read": true|false}`，不使用切换接口；单条清除只移除该消息。全部已读和全部清除均作用于当前用户全部消息，全部清除必须经客户端二次确认，且不影响关联发布、资产或失败记录。每次读写或清除均返回最新全量 `unreadCount`，并经用户级 SSE 向同账号其他已连接标签页推送未读数变化；抽屉已打开的标签页重新获取完整列表，未连接标签页在下次打开抽屉或恢复连接时经 REST 对账。SSE 不携带私有签名 URL、资产快照或内部错误。
- 官方消息不自动过期，已读消息保留至用户主动清除。单条清除和全部清除均写入 `deleted_at`，对用户不可恢复；列表和未读数均排除已清除消息。全部清除不返回删除条数，只返回新的 `unreadCount`，客户端随后重新获取完整列表。清除消息不删除关联图片、不撤销发布，也不改变发布失败记录；审计、客服或自动归档策略留待未来独立设计。
