# AiVista 发现能力模块

> 对应迭代：迭代 7——灵感、关注与关键词搜索
> 当前状态：设计中
> 维护规则：本文记录发现能力的后端范围、接口契约、数据与运行约定；代码、测试和文档必须同步修改。

## 1. 目标与范围

在迭代 6 的公开灵感流基础上，为当前仍公开的作品补充三类发现列表；后续讨论与实现只围绕这三类进行：

- 灵感列表。
- 关注列表。
- 关键词查询结果。

各列表的排序信号、筛选规则、访问条件和刷新语义待后续确认。热门排序、评论、个性化画像、付费曝光和对私有/审核中内容的发现不在当前讨论范围。

## 2. 已确认约束

- 仅当前 `APPROVED` 且 `public_at` 非空的作品可被发现；撤销或失效后不得继续出现在结果中。
- 图片项继续使用 `GenerationAssetImageResponse`；不得创建第二套图片响应 DTO。
- 公开内容与现有灵感流一致，不返回会话历史、对象键、审核记录、系统提示词或内部上下文。
- 所有列表采用服务端稳定排序与不透明游标；不得使用客户端页码推算。
- 灵感列表与关键词查询允许匿名访问；关注列表要求登录。无论访问者身份如何，均不得突破公开作品的可见性边界。
- 灵感页和发现能力不订阅 SSE；刷新或重新进入时读取服务端快照。

## 3. 关键决策记录

已确认发现页只包含灵感列表、关注列表和关键词查询结果；关键词查询只匹配公开作品的标题和描述。以下事项待讨论确认后写入本表：关键词匹配方式、三类列表的路由与接口是否拆分、灵感/关注/搜索结果的排序语义、数据库索引或外部检索服务、匿名限流和缓存策略。

| 决策事项 | 最终结论 | 原因与取舍 | 对实现的影响 |
| --- | --- | --- | --- |
| 发现列表范围 | 灵感列表、关注列表、关键词查询结果 | 作为迭代 7 后续讨论的共同边界。 | 不实现热门排序或其他未确认的发现入口。 |
| 访问条件 | 灵感列表与关键词查询允许匿名访问；关注列表要求登录。 | 关注关系属于当前登录用户；三类结果都不能突破公开可见性边界。 | 关注列表接口必须鉴权，匿名访问返回现有未认证错误；其余两类接口兼容匿名查看者。 |
| 搜索字段 | 仅匹配公开作品标题与描述。 | 首版不检索提示词、作者昵称、评论或标签。 | 查询条件、索引与后续排序设计只以标题和描述为基础。 |
| 搜索输入边界 | 前端仅传递一个 `keyword` 字符串；后端负责校验、规范化、拆词、匹配与排序。 | 不让 Web 或未来 App 自行定义分词、权重或布尔语法，保证所有客户端的搜索语义一致。 | 不接收前端传递的 tokens、权重或排序参数；空白处理、长度、单字符查询和限流策略待确认。 |
| 接口组织 | 采用三个语义独立的列表接口：灵感、关注与搜索。 | 三类查询的认证、输入、缓存和后续限流约束不同，不通过单一接口的 `mode` 参数隐式分支。 | 保留现有公开灵感接口；新增关注与搜索接口；三者复用统一图片 DTO 和 `{ items, nextCursor }` 分页响应。 |
| 关注列表排序 | `public_at DESC, id DESC`。 | 关注流以当前用户所关注作者的最新公开作品为唯一排序目标，不叠加推荐信号。 | 游标编码最后一条记录的 `publicAt` 与 `imageId`；查询使用稳定 keyset 分页。 |
| 分页批大小 | 三类列表每次最多返回 60 个作品；客户端不传 `limit`。 | 瀑布流的卡片高度不一，但一次请求的图片数量应由服务端统一限制，避免客户端任意放大读取量。 | 服务端常量设为 60；当仍有后续数据时才返回 `nextCursor`。 |
| 灵感排序信号 | 发布时间、单图点赞数、作者粉丝数、作者获赞总数；不加入随机排序。 | 同时兼顾新鲜度、单作品反馈和作者的社区信号，并保证同一排序快照中顺序可复现。原始计数不能直接相加。 | 需使用归一化后的综合分数；具体归一化口径、权重、衰减周期和候选内容范围待确认。 |
| 灵感排序一致性 | 使用全站共享、版本化的排序快照；不为每个用户保存一份列表。 | 点赞、关注和作者获赞会改变实时信号，实时重算会使游标产生重复或漏项；无个性化和随机排序时，共享快照的成本最低。 | 首次请求绑定当前 `snapshotId`，后续游标必须继续读取同一快照；新快照后台构建完成后原子切换。旧快照保留至游标过期。 |
| 快照构建与可见性 | 快照以一致性只读视图读取原始信号，在独立表中构建为 `BUILDING`，完成后切换为 `ACTIVE`；查询时仍实时过滤已撤销、删除或不再 `APPROVED` 的作品。 | 快照构建不应使用业务行锁，不能阻塞点赞、关注或发布写入；当前可见性与审核状态优先于历史快照完整性。 | 构建过程不得更新业务计数或覆盖活跃快照；失效快照条目被跳过并向后补足，无法补足时允许少于 60 项。刷新周期、游标有效期和旧快照保留期待确认。 |
| 搜索排序信号 | 在灵感排序信号基础上，标题和描述的关键词匹配优先。 | 搜索首先回答用户的明确查询，再在同等相关内容中兼顾质量与新鲜度。 | 固定排序键为 `matchLevel DESC, textScore DESC, snapshot.rankPosition ASC, imageId DESC`；具体匹配等级和文本分数规则待确认。 |
| 搜索匹配策略 | 倾向使用 MySQL 全文检索加 n-gram 召回候选作品，并由后端按固定规则计算最终匹配等级和文本分数。 | 中文检索不能只依赖普通英文分词；也不能将每次动态变化的全文检索浮点相关性直接作为游标边界。 | 实施前必须核验部署 MySQL 版本与 n-gram parser 可用性；当前项目尚无全文检索索引。多关键词的 AND/OR 语义、短语规则、查询长度及限流待确认。 |

## 7. API 与权限

采用三个语义独立的接口，不使用 `mode` 参数混合不同的权限和输入规则：

| 方法与路径 | 访问条件 | 已确认参数与响应 |
| --- | --- | --- |
| `GET /api/inspirations` | 匿名或登录 | 保留迭代 6 的公开灵感入口；`cursor` 可选；每批最多 60 项。 |
| `GET /api/inspirations/following` | 必须登录 | `cursor` 可选；每批最多 60 项；仅查询当前登录用户关注作者的当前公开作品。 |
| `GET /api/inspirations/search` | 匿名或登录 | `keyword` 必填、`cursor` 可选；每批最多 60 项；只查询当前公开作品标题与描述。后端负责输入规范化与匹配；长度、空白、单字符查询和非法输入规则待确认。 |

三者均返回 `GenerationAssetImageResponse` 列表与 `nextCursor`，不创建第二套图片 DTO。每个游标必须绑定创建它的接口语义与服务端稳定排序；关注游标绑定最后一项的 `publicAt`、`imageId`，灵感游标绑定 `snapshotId`、排序算法版本和最后一项快照名次，搜索游标额外绑定规范化 `keyword` 的摘要和最后一项文本排序键。跨接口、跨排序、跨快照或跨搜索词使用游标均为无效请求。后续仍需确定排序公式、游标有效期、搜索输入校验、数据库索引、匿名限流和缓存策略。
