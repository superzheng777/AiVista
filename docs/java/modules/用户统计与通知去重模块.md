# AiVista 用户统计与通知去重模块

> 对应迭代：社区身份与互动后续改造
> 当前状态：已完成
> 维护规则：记录用户统计、通知去重与共同事务边界；原始社区接口见[社区身份与互动模块](社区身份与互动模块.md)。

## 1. 目标与范围

将关注数、粉丝数和作者获赞数从用户主表拆至 `user_stats`；统一关注、点赞的通知去重，移除重复载荷；整理发布、审核、点赞、关注的锁顺序，并提供有界的整事务死锁重试。

关系、计数、通知和对应 Outbox 保持同一 MySQL 事务，不增加 Redis、MQ 或统计分片。[点赞系统优化](点赞系统优化.md)仍是独立的未实施异步方案，不代表当前事实。

## 2. 已确认约束

- 关注通知按同一对用户首次关注去重；取消后恢复关注不重复通知。
- 点赞通知按同一用户、同一作品、同一发布周期去重；新发布周期视为新作品，可以再次通知。
- 自赞计入作品点赞数和作者获赞数，但不通知自己。
- 取消关注、取消点赞物理删除关系；撤销发布清除当前周期点赞并扣减作者获赞数。
- 通知软删除仍保留去重依据；再次互动不恢复旧消息、不重置已读状态、不再次推送。
- 计数只随关系实际变化更新；通知已存在不阻止计数和搜索同步提交。
- 本轮开发数据无需保留，直接重置项目数据库并初始化最终表结构；OSS 由用户另行清空，联调用户 ID 从 10 开始，避免重用旧用户的对象路径。

## 3. 关键决策记录

`users` 保存身份、资料和 `likes_public` 偏好，`user_stats` 保存高频统计。关系表、通知表继续通过外键关联用户身份，不改为关联统计表。这样可以隔离用户资料写入与计数更新，但热门作者的统计行仍可能发生锁等待。

通知表保留消息查询和展示需要的结构化字段，以 `(recipient_user_id, dedup_key)` 唯一约束决定是否创建新通知。业务键由服务端生成，不用于解析身份、访问授权或客户端显示。

保留现有 REST 接口：关注和点赞使用 PUT 确保关系存在、DELETE 确保关系不存在，成功返回 204；公开资料字段保持不变。数据库内部重构不要求前端改动。

## 5. 设计与实现

### 用户统计

注册事务依次创建用户、零值统计行和同意记录。统计缺失视为完整性错误，互动路径不执行懒创建、不用零值掩盖。公开资料由 `User` 和 `UserStats` 组装，认证实体不混入联查统计字段。

关注实际变化后，按用户 ID 升序执行双方统计的原子 UPDATE；UPDATE 自身取得行锁，不再显式锁定用户主表。点赞、取消点赞、撤销发布在取得图片及发布状态锁后修改关系、作品计数与作者统计。撤销时实际删除的本轮点赞数量必须等于作品计数，否则整个事务回滚；只有删除数量大于零才扣减作者统计，零点赞撤销不执行统计行 UPDATE。

### 通知写入

`InteractionNotificationWriter` 统一处理自赞通知过滤、互动消息创建及通知 Outbox，点赞服务不重复判断通知接收人。普通 INSERT 仅在命中 `uq_notifications_recipient_dedup` 的 MySQL 1062 错误时视为已有通知；外键、字段和其他约束错误继续抛出并回滚业务事务。不使用 INSERT IGNORE 吞掉通知持久化错误。

互动固定文案由前端根据 `eventType` 展示，不再保存 title/content 或重复身份 JSON。官方审核消息继续保存标题、正文、违规项等元数据，同时写入发布版本和去重键。审核状态的条件更新只允许当前 PENDING 周期完成一次。

### 事务与锁顺序

- 关注：关系变更 → 按 ID 升序更新统计 → 首次通知 → 通知 Outbox。
- 点赞：图片及发布状态锁 → 点赞关系 → 作品计数 → 作者统计 → 搜索 Outbox → 首次互动通知及其 Outbox。
- 撤销：图片及发布状态锁 → 本轮点赞关系清理 → 非零作者统计扣减 → 发布状态清理 → 搜索 Outbox。
- 审核结果：先通过与点赞、撤销相同的锁定查询获取图片及发布记录，重新检查版本/PENDING，再更新发布状态、官方通知与 Outbox。远程审核在该事务之外。

`RetryingTransaction` 使用 TransactionTemplate；仅对 MySQL 1213 / SQLSTATE 40001 重试整个事务，最多 3 次尝试，失败间隔为 10–30ms 乘重试序号。已加入外层事务时不局部重试，由最外层负责。限流在事务重试之外，每次 API 请求只计一次；校验、外键、其他数据库错误不重试。

发布 upsert 在更新已有记录时可能返回 2，业务接受正的影响行数，避免撤销后再发布被错误回滚。

## 6. 数据模型与配置

`user_stats(user_id PK/FK users.id, following_count, follower_count, received_like_count)`，三个计数均为非负 bigint。正常更新仅命中已有行，并在扣减前校验数量足够。

`user_notifications` 保留 `id`、`recipient_user_id`、`category`、`event_type`、`actor_user_id`、`asset_id`、`publication_version`、`title`、`content`、`metadata_json`、`created_at`、`read_at`、`deleted_at`，新增 ASCII 二进制排序的 `dedup_key VARCHAR(160)`。title/content 可空，官方内容由业务写入。

| 通知 | 去重键 |
| --- | --- |
| 首次关注 | `follow:{actorId}:{recipientId}` |
| 本周期首次点赞 | `like:{actorId}:{assetId}:{publicationVersion}` |
| 发布审核结果 | `publication:{assetId}:{publicationVersion}:{status}` |

唯一索引为 `UNIQUE(recipient_user_id, dedup_key)`，替代旧的包含可空图片字段的互动联合索引。去重不受 read_at/deleted_at 变化影响。

本轮用户明确授权废弃旧开发数据，因此最终结构直接写入 `V1__initialize_schema.sql`，保留既有 V2、V3 增量能力。旧库不能直接启动修改后的应用，也不能用 Flyway repair 绕过结构变化；需先停止后端，清空项目表，再由 Flyway 初始化。未来需要保留数据的环境须另写增量迁移。

本地 MySQL 连接从未提交的 `application-local.yaml` 读取，支持既有环境变量占位符；前端、Java、TS 与 MySQL 在本地，其余依赖使用已有服务器配置。

## 7. API 与权限

公开资料、关注、点赞、发布、通知分页及 SSE 契约保持不变。公开响应不包含统计存储细节或认证字段，`dedup_key` 不返回客户端。通知读取、已读和删除继续校验当前收件人。

关注与点赞关系幂等和通知幂等独立：取消后恢复关系会增加计数，但同一去重范围内不新增通知。新发布周期可以新增点赞通知；旧周期通知的作品预览继续按当前版本及可见性判断。

## 8. 异常场景、可靠性与安全

- 缺失统计行、扣减数量不一致、通知或 Outbox 持久化异常会回滚完整事务。
- 死锁重试不重新执行远程审核，也不重复消耗限流额度。
- 拆表消除了已识别的用户外键共享锁与用户计数排他锁交叉依赖；不能保证所有业务路径永不死锁，也不能消除同一作品/热门作者的写入热点。
- 唯一键保证通知只创建一次，不保证 SSE 只投递一次；客户端仍依赖 REST 快照对账。
- 未来物理删除通知时，若仍要求长期去重，必须另行保留去重凭据。

## 10. 后续边界

本轮不引入异步计数、统计分片或独立通知服务；只有测得热门行等待已影响目标吞吐和响应时间时，再讨论这些方案及其一致性取舍。OSS 由用户后续清理，不属于本轮自动执行范围。
