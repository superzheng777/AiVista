# AiVista 用户统计与通知去重模块

> 对应迭代：社区身份与互动后续改造
> 当前状态：设计中
> 维护规则：通知表方案已确认，用户统计拆表及联合迁移仍在讨论；本文件不代表代码已经实现。现有行为见[社区身份与互动模块](社区身份与互动模块.md)。

## 1. 目标与范围

统一关注和点赞通知的去重机制，清理互动通知的重复载荷；评估将关注数、粉丝数、作者获赞数从用户主表移至独立统计表的影响。两项改造共用点赞、关注事务，需要一起检查计数幂等、通知幂等、锁顺序和数据迁移。

本次讨论基于当前 MySQL 同步关系与计数、事务 Outbox 的实现。[点赞系统优化](点赞系统优化.md)另有尚未实施的 Redis/MQ 方案；本次不同时引入该方案，也不将本文件视为对其整份设计的确认或废弃。未来若采用异步计数，必须重新评估撤销发布的一致性条件。

## 2. 已确认约束

- 保留一张 `user_notifications`，保存消息盒子所需的结构化字段，并增加明确的业务去重键。
- 保留 `id`、`recipient_user_id`、`category`、`event_type`、`actor_user_id`、`asset_id`、`publication_version`、`title`、`content`、`metadata_json`、`created_at`、`read_at`、`deleted_at`。
- 使用 `UNIQUE(recipient_user_id, dedup_key)` 约束同一收件人的重复通知；去重键由服务端生成，不作为字段解析、访问权限或列表查询的依据。
- 关注通知按同一对用户首次关注去重，取消后重新关注不再创建通知。
- 只有通知首次成功插入，才创建对应的推送 Outbox 事件。重复通知不能阻止关系、计数以及必要的搜索同步正常提交。
- 删除通知采用逻辑删除，保留去重依据；后续重复互动不恢复旧通知、不重置未读状态、不重新推送。
- 清理互动通知 JSON 中与独立字段重复的用户 ID、图片 ID、发布版本；互动固定文案由事件类型生成。官方消息继续保存标题、正文及审核原因等必要内容。
- 不为通知去重而将点赞、关注关系改为逻辑删除；当前有效关系仍是关系状态与计数的依据。

## 3. 关键决策记录

### 已确认的通知职责

通知表保存消息历史和消息状态，业务去重键负责判断是否应创建通知。关系状态改变与通知首次创建是两个独立条件，不能用通知插入结果决定是否增加或扣减计数。

### 仍需收敛的事项

- `user_stats` 拆表目前为建议方案，尚未实施；建议保持同库、同步事务计数，不一并增加 Redis、MQ 或分片计数。
- 点赞通知去重是否跨发布周期尚未最终确认：沿用当前规则使用 `like:{actorId}:{assetId}:{publicationVersion}`；若同一图片终身只通知一次，则不包含发布版本。无论选择哪一种，结构化 `publication_version` 仍用于判断旧通知关联的发布周期。
- 撤销发布是否保留点赞是独立产品规则；在另行确认前，仍按当前删除本轮点赞并扣减获赞数的语义评估。
- 联合迁移采用短暂停写还是兼容发布，取决于部署要求，不能在持续写入下直接复制旧计数后切换。

## 5. 设计与实现

### 用户统计拆表建议

新增 `user_stats`，以 `user_id` 为主键，包含 `following_count`、`follower_count`、`received_like_count`，均为非负整数。`user_id` 关联 `users.id`；关系表和通知表仍关联稳定的用户身份，不改为关联统计表。`likes_public` 是用户偏好，继续属于用户主表。

新用户注册时，在同一事务创建用户、零值统计行及同意记录。老用户迁移时补齐统计行并与关系表核对。正常互动只更新已有统计记录，缺失统计行应作为完整性错误处理，不能静默跳过或以零值掩盖。

用户实体移除三个统计持久化字段，新增统计模型和数据访问；公开资料使用显式查询结果或由资料与统计组装响应，避免将关联查询结果混入 `users` 持久化实体。

### 涉及的现有入口

| 入口 | 拆表后的改动 |
| --- | --- |
| `AuthService.register` | 同事务创建统计记录 |
| `UserProfileService.getPublicProfile`、`PublicUserProfileResponse` | 查询并组装用户资料与统计，保持 HTTP 字段不变 |
| `UserFollowService` | 关注关系实际变化后更新双方统计；移除用于计数串行化的用户主表排他锁，保留用户存在性校验 |
| `GenerationImageLikeService` | 图片赞数仍写发布表，作者获赞数改写统计表 |
| `PublicationService.withdraw` | 本轮点赞删除数与图片计数一致后，扣减作者统计记录 |
| `UserNotificationMapper` 及通知创建逻辑 | 按统一去重键判断首次插入，首次成功时保存推送事件 |

### 两项改造的事务配合

关注或点赞的关系确实变化时，先更新相关计数，再尝试创建通知；通知已存在只跳过通知和通知推送事件。其他数据库错误必须使完整业务事务回滚。

关注涉及两条统计行，按用户 ID 升序更新。点赞及撤销保留图片与发布状态的事务协调，并采用一致的关系、统计、通知获取顺序。不得让某些入口先锁统计行再锁图片、其他入口反向获取。

审核结果落库也会修改发布记录并插入带用户、图片外键的官方通知，需要与点赞、撤销一起检查隐式锁。仅增加通知去重键不能解决这类锁顺序问题；去重冲突本身也会涉及索引锁。远程审核调用仍在短事务之外。

## 6. 数据模型与配置

### 通知字段

| 字段 | 作用 |
| --- | --- |
| `id` | 通知标识、消息操作、分页及 Outbox 引用 |
| `recipient_user_id` | 收件人、列表查询与操作权限 |
| `category`、`event_type` | 消息页签和具体事件类型 |
| `actor_user_id` | 互动发起人，可关联当前昵称头像 |
| `asset_id`、`publication_version` | 作品及其发布周期 |
| `dedup_key` | 同一收件人的业务通知去重；不需去重的通知可为空 |
| `title`、`content` | 官方消息内容；互动固定文案不再存储时需允许为空 |
| `metadata_json` | 审核违规项等额外数据，不重复存储已有身份字段 |
| `created_at`、`read_at`、`deleted_at` | 时间排序、已读与逻辑删除 |

### 迁移建议

通过新增 Flyway 迁移演进已有数据库，不修改已执行的初始化脚本。先新增统计表和可空的去重字段，再补齐和校验数据，切换业务读写，最后删除旧用户统计列、旧点赞通知去重索引及失效代码。

历史关注通知可能重复。可保留全部历史消息，仅让按创建时间和 ID 排序最早的一条持有规范去重键，其余保持空键；必须包括已逻辑删除的消息，且迁移不得重新发送历史通知。点赞若改为跨周期去重，同样检查跨周期历史重复。

短暂停写模式下，需覆盖注册、关注、点赞、撤销、审核通知写入等相关入口和后台任务。在线兼容发布则需要旧新计数同步、历史回填一致性和新旧通知写入兼容，不能仅依靠一次回填。旧应用实例全部退出前不得删旧列。

## 7. API 与权限

建议保持现有 HTTP 字段、点赞和关注成功时的 `204`、通知分页和未读接口，以及 SSE 的 `notificationId` 载荷。前端主要做回归验证；公开用户资料不得因关联统计表而暴露认证字段。

通知读取与已读、删除仍以收件人校验权限；`dedup_key` 不返回客户端，也不参与授权判断。

## 8. 异常场景、可靠性与安全

- 计数只随关系的真实变化增减，重复请求不改变计数。
- 重新关注可以增加计数但不新增通知；这是预期行为，不属于写入失败。
- 预期的去重冲突作为“通知已存在”处理，不能吞掉外键、字段或其他约束错误。
- 统计写入或必要通知持久化失败时，关系、计数和 Outbox 一起回滚。
- 下架仍按当前规则原子清理本轮关系与计数，历史通知保留；旧通知是否能返回作品仍检查发布版本。
- 拆表隔离用户主表与计数写入，不能消除热门作者统计行的写入热点，也不等于消除所有死锁。
- 通知只创建一次不代表 SSE 仅投递一次；客户端继续按现有 REST 快照对账。

## 9. 测试与验收

待实施时验证：新旧用户统计行完整；公开资料响应兼容；重复关注和点赞计数不变；取消再操作计数恢复但通知去重；消息软删除后不重新通知；自赞不通知；撤销及跨版本行为正确；失败时完整事务回滚；历史去重键回填不产生新消息。

真实 MySQL 并发验收覆盖相互关注、相互点赞、重复请求、点赞与撤销、审核与撤销、通知重复插入。Mock 测试不能证明数据库锁行为；需检查锁等待、死锁错误及最终关系和计数是否一致。

本次只记录设计，未执行本方案的数据库迁移、业务实现或验收。

## 10. 后续边界

不因这次拆表自动引入异步计数、统计分片或独立通知服务。若未来物理清理通知记录，又要求长期只通知一次，应保留独立的去重依据。用户主表拆统计与通知去重可分步骤实施，但共同事务路径与迁移必须统一验证。
